# Relay should remember useful working agreements

Relay should remember **explicit, durable facts and preferences that change how it helps the user**: their recurring work, explanation needs, tool defaults, collaboration expectations, and practical constraints. Its first priority should be making that knowledge easy to find, correct, and retire. Competitors offer useful precedents for scoped instructions, editable memory files, and learned recollections, but those mechanisms differ substantially in availability, ownership, and control. For card #M7RY, the right implementation is the existing Globals memory store with a default **User memory** view and an optional **Interview me** conversation that proposes concise facts and saves only those the user selects. That scope is supported by the inspected working-tree implementation; automatic background inference, true erasure, and new global use/generate switches are future work, not current features. The product promise should be “review and improve the saved context Relay uses to help you,” with an honest explanation of project precedence, context limits, and model exposure.

Research and source retrieval date: **22 September 2026**. This report synthesizes both supplied research notes, reopens the principal vendor sources, and inspects Relay source code. There was no earlier report. Competitor findings describe documentation, not hands-on certification of every installed version or plan. Relay findings describe the shared checkout during #M7RY implementation, including uncommitted changes; they do not certify a released binary. Recommendations and example answers below are design proposals, not established facts about this user.

## Useful memory changes future assistance without collecting a biography

The practical test for a memory is whether it will prevent a recurring misunderstanding or improve a future decision. “Give brief progress updates, then explain material risks” passes that test. A transcript of today's debugging session does not: it belongs with the conversation or work record. A repository's build command belongs with its project. An executable procedure belongs in a skill or action. **User memory describes the person across projects; the subject of a fact alone does not determine its scope.** Claude Code illustrates this distinction particularly well: its auto-memory categories include user information, while its default auto-memory directory remains project-specific. ([Claude Code memory](https://code.claude.com/docs/en/memory))

The following taxonomy is a recommended editorial policy for Relay's helper and review surface. “Useful” means useful when explicitly supplied or confirmed, with relevant exceptions preserved. These are hypothetical examples, not inferred preferences.

| Category | Useful candidate memory | Not useful as durable user memory | Appropriate handling |
|---|---|---|---|
| Work and expertise | “I mainly use Relay for empirical research and maintaining Python tools.” | A complete employment history; an inferred occupation from repository names | Save a short description only when it changes examples or assistance; ask about explanation depth separately. |
| Communication | “Start with the outcome; give details when they explain a failure or trade-off.” | “The user is impatient” inferred from a correction | Save the requested behavior, without a personality label. |
| Tool defaults | “For new Python projects, prefer uv unless project instructions say otherwise.” | “This repository uses Poetry” promoted to a universal preference | Preserve the default and exception; keep repository requirements local. |
| Verification | “Report the checks actually run and any unresolved failure.” | Today's test result or a permanently cached claim that a build passes | Save the evidence preference; put current results on the work record. |
| Collaboration and autonomy | “Proceed with routine reversible work; ask when a product decision changes scope.” | “Never ask permission” treated as authority to deploy or send messages | Save a working preference, never an authorization credential. |
| Environment and routing | “I often work over SSH; distinguish commands for the remote host from local commands.” | Passwords, private keys, access tokens, or a stale assumption about the active host | Store names or roles only when needed; inspect current connection state. |
| Long-running work | “For long jobs, give a restart command and a log location.” | A PID, temporary output path, or one-off deadline | Save the workflow preference; retain job state in its task/session. |
| Accessibility and input | “I dictate prompts; ask when a likely transcription error changes the request.” | A diagnosis inferred from voice use or typing patterns | Save the requested accommodation without demanding medical context. |
| Writing and domain conventions | “Use plain language and distinguish evidence from interpretation.” | A full style manual duplicated across many cards | Save the concise preference or an approved reference; keep long reusable guidance in an instruction or skill. |
| Personal logistics | “Use America/New_York when interpreting my scheduling requests.” | Travel location guessed from a timestamp; legal identifiers | Ask only when the work needs it; confirm whether a temporary exception should remain temporary. |
| Memory boundaries | “Do not propose memories from client-confidential work.” | A promise that saving this sentence implements enforceable exclusion or deletes old data | Treat it as guidance in #M7RY; stronger enforcement needs a separate feature. |
| Project knowledge | “This project requires scripts/relay-build.” | A user-wide rule applied to unrelated repositories | Save as project instructions or a project memory, outside the user-only helper tool. |

Prefer **one independently correctable fact per card**, expressed as an actionable statement with its condition. This makes “I prefer concise answers, except when learning an unfamiliar system” more useful than either “be concise” or a psychological profile. Do not extract religion, health, politics, relationships, financial circumstances, or identity attributes merely because they appear in accessible files. Even benign interests add little unless the user explains how remembering them helps. Memory quality should be judged by fewer repeated corrections and fewer inappropriate applications, not by the number of facts collected.

Explicit instructions and factual context should remain conceptually distinct even when both use existing memory cards. “I maintain research software” supplies context; “summarize test evidence before calling work finished” requests behavior. Neither is a substitute for the current request or enforced permissions. Relay already marks injected memory as lower-priority saved context, with current user requests and Relay rules taking precedence. ([Relay memory selection and prompt construction](../backend/relay_core/memories.py))

## Competitors separate authored guidance from learned recollections

“Memory” covers several different products: authored instruction files, notes written by an agent, hosted retrieval services, and ordinary session context. Comparing them as a single yes/no capability hides the design choices Relay needs to make. The table distinguishes documented behavior from unresolved details and dated features.

| System and availability | Scope, creation, and retrieval | Review, correction, and controls | Lesson for Relay |
|---|---|---|---|
| **Warp Rules**, current documentation | Global rules plus project/subdirectory `AGENTS.md` or legacy `WARP.md`; more specific project rules take precedence. Rules are selected for relevance. | Personal → Rules → Global supports adding, editing, and deleting rules; `/add-rule` opens the flow; applied rules appear in references. ([Rules](https://docs.warp.dev/agents/capabilities/rules/)) | Make personal guidance directly discoverable and show where it applies. |
| **Warp Agent Memory**, restricted research preview | Enabled per design-partner team. Warp-hosted personal, agent, and team stores support automatic extraction, explicit remembering, conflict supersession, provenance, and relevant retrieval. Local Warp Agent and cloud agents are supported; local third-party harnesses are excluded from this preview. | Store attachments have read/write access and instructions. New agents can opt out of their default auto-memory store at creation. Exact memory deletion and retention guarantees were not established. ([Agent Memory](https://docs.warp.dev/agents/agent-memory/)) | Borrow ownership and provenance concepts without claiming universal availability or copying a hosted learning service into #M7RY. |
| **Claude Code**, current documented defaults | Authored `~/.claude/CLAUDE.md` is cross-project; project guidance is separate. Automatic Markdown notes default to `~/.claude/projects/<project>/memory/`. Startup loads at most the first 200 lines or 25 KB of `MEMORY.md`; topic files load on demand. | `/memory` opens memory files and controls auto memory; notes can be edited or deleted. Default storage is machine-local and shared across worktrees of the project. ([Memory](https://code.claude.com/docs/en/memory)) | Show both what a fact concerns and its actual scope; distinguish a saved fact from the subset initially loaded. |
| **Codex**, current documented memory feature; off by default | Authored global/project `AGENTS.md` instructions coexist with local learned memory under `~/.codex/memories/`. Learned memory is separate from ChatGPT web memory. Background processing skips active/short-lived chats and redacts secrets. | CLI/desktop `/memories`; per-chat use and contribution controls; desktop Personalization settings. Generated files are inspectable, but manual editing is not the recommended primary control. IDE sessions use their connected host's store. ([Memories](https://learn.chatgpt.com/docs/customization/memories)) | If Relay later adds learning, distinguish using previous memories from contributing new ones. Do not imply account-wide synchronization from a local store. |
| **OpenCode**, current native rules documentation | Global `~/.config/opencode/AGENTS.md` and project `AGENTS.md`; `/init` inspects the project and asks targeted questions as needed. Configured instructions can include files/globs/URLs. References inside `AGENTS.md` are not automatically parsed. | Directly editable files; native rules take precedence over supported Claude-compatible fallbacks. A native automatic personal-memory review service was not established by these sources. ([Rules](https://opencode.ai/docs/rules/)) | Reuse an understandable editable representation and ask only questions that available context cannot answer. |
| **Cursor**, current rules; historical Memories caveat | Current User Rules apply across projects to Agent Chat; project `.cursor/rules/*.mdc` supports explicit application modes. Team rules outrank project rules, which outrank user rules. Rules do not apply to Tab or Inline Edit. | Customize → Rules and `/create-rule` expose authored guidance. Do not treat historical learned Memories as a current universally available feature. ([Rules](https://cursor.com/docs/rules)) | A personal entry point is useful even without automatic learning; document which surfaces consume its content. |
| **VS Code agent memory**, current local-memory documentation | Separate local user, repository, and session scopes; agents can write notes during work or after explicit requests. User scope crosses workspaces and initially loads its first 200 lines. | `Chat: Show Memory Files`, clickable memory references, and `Chat: Clear All Memory Files`; ask the agent to update/delete individual files. ([Memory](https://code.visualstudio.com/docs/agents/run/memory)) | Keep task scratch space separate from durable preferences and expose review access near the conversation. |
| **GitHub Copilot Memory**, paid-plan public preview | Hosted repository facts and cross-repository personal preferences. Repository facts carry code citations validated against the current branch; unused memories expire after 28 days, with use/validation able to reset the timer. | Personal/repository settings expose review and deletion. Managed-plan preferences belong to the active billing entity; administrators can export/delete them. ([Concepts](https://docs.github.com/en/copilot/concepts/agents/copilot-memory), [Personal controls](https://docs.github.com/en/copilot/how-tos/use-copilot-agents/copilot-memory/manage-for-yourself)) | Ownership, audience, and retention need explicit explanations; “personal” does not necessarily mean inaccessible to an organization. |

These differences also prevent a universal precedence rule. Relay, Warp, and Cursor do not necessarily order every instruction class in the same way. Codex discovers instructions from the repository root toward the working directory, with more specific later guidance overriding earlier guidance; its authored instruction chain has a default **32 KiB** limit and is built once per run. That is an instruction-loading limit, not a documented learned-memory budget. ([Codex AGENTS.md](https://learn.chatgpt.com/docs/agent-configuration/agents-md)) Relay should describe its own behavior directly rather than borrow another product's terminology or limits.

Version caveats matter especially for Cursor. Its June 2025 release introduced a project-scoped Memories beta; a November 2025 vendor-hosted support response says it was removed beginning with **2.1.x** and recommends exporting memories into rule content. The latter is a dated support statement, not a hands-on guarantee about every channel. Current rules documentation is the sound basis for a present-day comparison. ([Cursor 1.0 announcement](https://cursor.com/en-US/changelog/1-0), [Removal and export response](https://forum.cursor.com/t/are-my-memories-gone/144057/3)) Likewise, an OpenCode ecosystem listing for `opencode-supermemory` establishes an optional extension, not native installation or retention guarantees. ([OpenCode ecosystem](https://opencode.ai/docs/ecosystem/))

No common, established personal-profile interview emerged from the reviewed sources. The strongest precedents are assisted configuration: Claude Code documents an interactive initialization flow gated by `CLAUDE_CODE_NEW_INIT=1`, and VS Code's `/create-instructions` asks clarifying questions before producing guidance. These support a **short, adaptive, reviewable interview** as a design inference; they do not establish that interviews improve task success. ([Claude Code commands](https://code.claude.com/docs/en/commands), [VS Code custom instructions](https://code.visualstudio.com/docs/agent-customization/custom-instructions)) The notes identify a locally installed Codex package version 0.155.1, but inspecting its launcher did not verify runtime memory behavior. Other comparisons are tied to the retrieval date, not invented client-version guarantees.

## Relay can make existing memory legible without adding another store

The inspected #M7RY implementation makes **User memory the default filter in Globals**, alongside **Aliases**, **Instructions**, and **All records**. The list includes readable summaries, status, and project-override indications; search covers labels, summaries, source paths, and identifiers. Selecting a record reveals its source and a plain Markdown editor with Save, Cancel, and Retire. This is a dedicated entry point into existing records, not a second profile database or a structured biography form. ([GlobalsPane implementation](../src/GlobalsPane.cpp))

That is the right first release. A user can answer “what does Relay think it knows about me?” and correct the source directly without entrusting all maintenance to an agent. Keeping aliases and imported instructions accessible through neighboring filters also avoids pretending that every persistent influence on behavior is a personal memory. The introductory copy already explains that applicable memories go to the chosen model and that retirement retains the file and history. Preserve that clarity. A source-path label is valuable to a technical user, but the primary description should remain the fact and where it applies. ([GlobalsPane constructor and display](../src/GlobalsPane.cpp))

The lifecycle below distinguishes implemented mechanisms from helper behavior and future controls. **Saved, active, eligible, and actually included are different states.** A record can be saved successfully without appearing in a particular turn's memory context.

| Stage | Current #M7RY / reused behavior | Necessary interpretation |
|---|---|---|
| Answer or candidate | The helper asks questions and proposes exact facts before saving selected answers. | An interview answer is not automatically a durable memory card; it can still remain in ordinary conversation history. |
| Create or edit | Existing full-Markdown save path; stable identity and name; user tool restricts records to `scope: user`. | Prefer updating the existing fact over creating a competing synonym. Direct “remember this” requests already authorize saving. |
| Resolve concurrent edits | `base_hash` is checked using the existing Globals write path; changed files require reload. | The helper must report a conflict instead of silently replacing a newer correction. |
| Select for a turn | Active non-team cards; pinned or matching workspace paths; project names override matching global names; supersession is applied. | Global location alone does not guarantee inclusion. A same-name active project record shadows a global before path eligibility is filtered. |
| Fit the context | Memory prompt section is capped at **16 KiB of UTF-8 text**, including framing; final content can be truncated. | This is neither 16,384 tokens nor a storage allowance. Pinned means eligible across projects, subject to selection and budget. |
| Correct | Edit the same card and preserve its identity; helper is instructed to use the latest hash. | A correction changes future saved context, not text already sent to a model. |
| Retire | Existing retirement marks the record retired, archives it, and retains history. | **Retirement is not erasure** from files, histories, backups, or previous conversations. |
| Purge or pause all use/learning | No true purge and no new global use/generate switches in this implementation. | Do not label retirement “delete forever” or imply controls that have not been built. |

These details come from the existing selector and the shared Globals validation/write mechanism, plus the new user-only tool. ([Memory selector](../backend/relay_core/memories.py), [Globals protocol](../backend/relay_core/globals_protocol.py), [User-memory tool](../backend/relay_core/app_tools.py)) The loader is workspace-path based; it should not be advertised as semantic search or automatic relevance ranking. It processes project candidates before globals, and its cap can truncate a card's text. This argues for short facts and eventual visibility into actual inclusion, rather than filling the store with long personal essays.

The first release should retain its current plain editor and explanatory copy. A later improvement should show an **effective memory view for a specific turn**, with “included,” “overridden by project,” “superseded,” “retired,” or “excluded by limit” reasons. Today the UI explains constraints, but it is not a complete per-turn inclusion ledger. Similarly, recording `source: user interview` and a reviewed date is useful provenance, but it is not a structured origin system with reliable links to every original statement. Those distinctions keep the report's recommendations from becoming unsupported launch claims. ([Current display](../src/GlobalsPane.cpp), [Interview guidance](../backend/relay_core/agent_context.py))

## The interview should negotiate a few useful facts, one question at a time

**Interview me should start an ordinary conversation with the existing Globals helper.** The current implementation focuses the existing helper and submits an ask through the normal agent queue. Its request says to inspect saved memories, ask one relevant question at a time, allow skipping or stopping, and show proposed facts before saving. There is no separate interview engine, questionnaire database, or hidden learner. ([Interview button wiring](../src/RelayWindow.h), [Globals helper instructions](../backend/relay_core/agent_context.py))

The helper should first list and inspect relevant existing user memories, then start with an uncovered need. For a new user, “What work do you mainly want Relay to help with?” is a useful opener. For a returning user whose work is already described, “What do you keep having to correct me about?” is better. The next question should follow the answer: research work suggests evidence and reproducibility; remote development suggests local-versus-SSH handling; unfamiliar tools suggest explanation depth. Do not ask a fixed list of biographical questions simply because a category is empty.

The table is a bank of possible branches, **not a form to administer in full**. An initial interview should stop after a few useful answers and offer its candidate facts; completing every topic is unnecessary.

| Trigger in the conversation | One possible next question | Hypothetical candidate, if confirmed |
|---|---|---|
| Work is unknown | “What do you mainly want Relay to help you do?” | “Uses Relay mainly for research software and analysis workflows.” |
| Work is known but friction is unclear | “What do you most often have to correct an assistant about?” | A specific correction, such as “Report failed checks explicitly.” |
| User asks for brief answers | “When would a fuller explanation be useful?” | “Keep routine updates brief; explain unfamiliar concepts and consequential trade-offs.” |
| User names a preferred tool | “Is that your default everywhere, or only for this project?” | “Prefer uv for new Python projects unless the repository specifies another tool.” |
| User frequently works remotely | “What should I do differently when your work is on an SSH host?” | “State which host a command or result belongs to.” |
| User wants autonomy | “Which decisions should I bring back to you before continuing?” | “Ask about changes to product scope; continue routine reversible work within the request.” |
| User values reproducibility | “What evidence makes a task feel finished to you?” | “Include the checks run and enough detail to reproduce material results.” |
| User runs long jobs | “How would you like long-running jobs handed back?” | “Give the job's log location and the command needed to resume or inspect it.” |
| User mentions voice or accessibility | “What would make Relay's questions and output easier to use?” | A requested accommodation, without inferring a diagnosis. |
| Several candidates exist | “Which of these exact facts should I remember?” | Save only the selected statements, incorporating any correction first. |
| User signals sensitive work | “Is there anything you want excluded from proposed memories?” | A boundary preference, with no claim that it implements deletion or technical filtering. |

Before writing, present each candidate as a short statement with its intended cross-project scope. If an answer belongs to the project, explain that placement rather than forcing it through the user-memory tool. After confirmation, list existing records again when necessary, read the latest version/hash of a matching record, update it or create one small new card, and report exactly what was saved and where to review it. A user who explicitly says “remember that…” has already authorized the relevant save; repeatedly asking for confirmation adds friction without clarifying intent. The implemented helper guidance expressly distinguishes those requests from interview candidates. ([Helper instructions](../backend/relay_core/agent_context.py))

For example, an answer “I like concise answers, but I am learning Rust” should prompt clarification about whether extra Rust explanations are wanted; it should not become “beginner programmer.” An answer “use npm here” should remain local unless the user says it is a global default. If the user skips a topic, the helper should proceed without saving a guessed answer. If the user stops before confirming candidates, the helper should save none of those candidates. Ordinary chat history remains a separate retention surface.

The **confirmation rule is agent guidance, not a separate cryptographic or UI-enforced consent token**. The tool enforces user scope and reuses write permissions, validation, and hash conflict protection, but the inspected implementation does not independently prove that a prior user confirmation exists for each fact. Product evaluation should therefore exercise the conversational behavior as well as the storage API. An autonomy preference also never grants permission to send messages, spend money, or bypass current restrictions. ([Tool schema and handler](../backend/relay_core/app_tools.py), [Helper instructions](../backend/relay_core/agent_context.py))

## Ship clear review and correction first, then improve observability and control

The implementation recommendation is to complete and verify #M7RY as scoped: **existing memory cards, a default User memory view, readable summaries/search, the plain source editor, and an optional adaptive interview using the existing helper**. Keep `app_user_memory` narrow: list/get/save/retire for user-scoped records, preserving the existing validation and optimistic concurrency path. This is enough to make personal context understandable and editable without a new inference service. The code inspection supports that architecture; this report does not claim to have run its GUI or behavioral tests. ([GlobalsPane](../src/GlobalsPane.cpp), [App tools](../backend/relay_core/app_tools.py), [Globals write path](../backend/relay_core/globals_protocol.py))

Verification should establish both usefulness and boundaries. A new user should find User memory without knowing that Globals stores it, add a fact manually, edit it, and retire it with the retention meaning understood. A returning user should get questions that skip known facts; an explicit correction should update the existing record; a stopped interview should create no unconfirmed memory cards. Concurrent editing should produce a visible conflict while preserving the user's newer text. Scope tests should reject non-user records through the helper tool, and context tests should cover project name overrides, path matching, supersession, retired/team exclusion, and the byte cap. These are proposed acceptance scenarios, not results reported as passed here.

Future work should follow a deliberate order. First, make actual memory use observable and make short factual editing easier while retaining source access. Add reliable provenance, review dates, and suggestions for resolving duplicates or stale facts. Then consider export and true purge, with an explicit specification of which stores, histories, conversation copies, indexes, backups, and remote copies are affected. Do not introduce a “Delete” label until its meaning is defined. An export should also distinguish Relay memory cards from other instruction sources that influence the agent.

Only after those foundations should Relay consider opt-in background suggestions or inference. That feature would need distinct controls for **using saved context**, **generating new candidates**, and **saving approved candidates**, with a per-conversation exclusion that has defined technical behavior. Codex's separation of memory use from contribution supplies a useful precedent, but Relay does not currently implement those new switches. ([Codex memories](https://learn.chatgpt.com/docs/customization/memories)) Automatic suggestions should remain proposals unless the user deliberately selects a different policy; they should not silently replace explicit preferences.

Privacy explanations should describe data flow in plain terms: where a memory resides, which selected model receives it when included, whether another user or organization can access it, and what retirement leaves behind. Local storage alone does not mean local inference. Managed Copilot ownership shows why a “personal” label cannot carry all those meanings by itself. ([Copilot ownership and retention](https://docs.github.com/en/copilot/concepts/agents/copilot-memory)) For Relay, cross-device synchronization, hosted retention, administrator visibility, and erasure propagation were not established by this narrow source inspection and should not be implied by the new review surface.

The open empirical question is whether the interview earns its interruption cost. Evaluate it with voluntary, local usability sessions: can users find and correct a saved fact; do proposed statements match their intended scope; how often do users reject or substantially rewrite them; and do later tasks require fewer repeated corrections? Compare a brief interview with manual entry and correction-driven remembering. Prefer these task outcomes to profile completeness, memory volume, or engagement metrics. No reviewed source establishes a causal benefit from a personal-memory interview, so the first release should keep it optional and easy to stop.

## Conclusion

Relay's opportunity is to make persistent assistance understandable across its changing agents and workspaces. A stable, editable record of working agreements can outlast a particular model or harness, provided the interface explains where each statement applies and the system never confuses a remembered preference with authority to act. The immediate design is deliberately small enough that users can inspect its entire meaning; future sophistication should earn its place by improving correctness, visibility, or control.

The strongest long-term differentiator would be an answerable question: “Why did Relay use this fact here, and how do I change that?” #M7RY supplies the review and correction foundation. Provenance, actual inclusion traces, and precisely defined removal controls are the next steps toward making that answer dependable.
