# Let evidence close Relay’s verification backlog

**Relay should not require a human button press to close every software development card.** It should require a current, claim-specific verification result for every card, reserve accountable human judgment for consequential or subjective claims, and let an authorized agent record and execute an owner’s explicit approval in chat. A click is one interface for a decision, not an extra safety property. The local audit counted **547 cards on 2026-09-24** in `needs-verification` (306) and `needs-qa-llm` (241), from 706 work cards in a live shared checkout; it was a point-in-time count, not a frozen baseline. Most of that queue cannot safely be closed from its status or metadata. The way to reduce it is to make evidence reusable, verify each claim against a suitable oracle, and escalate the smaller set that needs a person.

## Reported practice supports different gates for different work

**Reported practice, not a general safety result:** OpenAI described an experimental Codex repository where engineers work largely through prompts, human pull-request review is optional, agents seek other agent reviews, and agents often merge their own changes. Anthropic describes a different boundary: its Code Review system checks nearly every pull request but does not approve one, because approval is a human call. Amplitude reports automatically merging some low-risk pull requests after a custom risk classifier and Bugbot review, while routing higher-risk work to engineers. These are team-specific choices, not evidence that one closure gate suits Relay. ([OpenAI](https://openai.com/index/harness-engineering/); [Anthropic](https://claude.com/blog/code-review); [Cursor/Amplitude](https://cursor.com/blog/amplitude))

**Platform behavior also separates approval from a button.** GitHub can auto-merge after required checks and eligible reviews pass, and its protected branches can require both. A chat approval does not itself create a qualifying GitHub review when branch rules demand one. GitHub issue-closing keywords can close an issue on merge; Linear recommends a distinct “Merged” state before “Done” at release. Thus implementation, verification, formal PR approval, merge, release, and Board closure can be different events. Relay should define which event a card’s acceptance criteria require, then capture it once. ([GitHub protected branches](https://docs.github.com/en/repositories/configuring-branches-and-merges-in-your-repository/managing-protected-branches/about-protected-branches); [GitHub auto-merge](https://docs.github.com/en/pull-requests/how-tos/merge-and-close-pull-requests/automatically-merging-a-pull-request); [GitHub issue keywords](https://docs.github.com/en/get-started/writing-on-github/working-with-advanced-formatting/using-keywords-in-issues-and-pull-requests); [Linear releases](https://linear.app/docs/releases))

## Empirical evidence favors focused checks over an AI pass

**Empirical evidence:** a 2026 evaluation of GitHub Copilot code review on curated vulnerable code found missed SQL injection, cross-site scripting, and insecure deserialization cases. It does not estimate the false-negative rate on Relay pull requests, but it rules out treating a clean AI review as proof of security. An observational study of 1.5 million Microsoft review comments found that the share authors considered useful fell as changes spanned more files; this supports keeping human review focused and reviewable, without establishing a universal size threshold. ([Amro and Alalfi](https://proceedings.mlr.press/v318/amro26a.html); [Bosu, Greiler and Bird](https://www.microsoft.com/en-us/research/publication/characteristics-of-useful-code-reviews-an-empirical-study-at-microsoft/))

**Inference for Relay:** an AI reviewer should produce candidate defects, scenarios, and test gaps. A clean result means only that reviewer found none. Deterministic tests can close exactly the behavior they assert, provided the expected result, revision, environment, command, output, and artifact are recorded. UI quality, accessibility experience, architecture, security threat modeling, and high-consequence behavior need a live probe or accountable judgment. Risk ranking should set the order and depth of verification, not excuse missing evidence. NIST frames risk assessment as an input to decisions; its acceptance-sampling method requires a defined population, sample, acceptance number, and operating-characteristic curve. A sample of heterogeneous cards cannot certify unsampled claims. ([NIST risk assessment](https://csrc.nist.gov/pubs/sp/800/30/r1/final); [NIST acceptance sampling](https://www.itl.nist.gov/div898/handbook/pmc/section2/pmc243.htm))

## The 547-card audit reveals evidence debt

**Local audit:** the research note’s read-only scan of card front matter on **2026-09-24** counted 306 `needs-verification` and 241 `needs-qa-llm` cards, totaling **547**. A scan moments earlier found 705 total work cards rather than 706 because other sessions were editing the shared Board. In the two lanes, only 54 and 0 cards respectively had a `verify` block; 13 and 7 respectively had no structural `unverified_reasons()`. Those **20 are not proven closable**: the predicate checks record structure, while tests, signals, artifact quality, and the effective global Options setting can still block closure. A `## Verdict` heading alone does not establish a favorable independent verdict. This is an audit of repository records, not an empirical estimate of underlying software quality. See the [reproducible local audit](../research_notes/AI%20software%20verification%20policy/relay_backlog.md), [Board predicate](../backend/relay_core/board.py), and [QA defaults](../backend/relay_core/qa_policy.py).

**Current local policy matters.** The project’s `board.yaml` has no QA override; code defaults are `verification: ask`, a human requirement beginning at money stakes, no AI primary gate by default, and no sampling by default. The global Options value was not inspected by the audit. A card without a `verify` block can pass the structural gate with primary evidence alone, so missing risk metadata on legacy cards must not silently become a low-risk classification. The Board also checks relevant test results and open signals before movement, and unanswered Human QA questions or required sign-off receipts block `done`. These are existing mechanics, not evidence that all historic cards obeyed them. ([Local Board policy](../.board/POLICY.md); [Board format](../docs/BOARD-FORMAT.md); [QA policy code](../backend/relay_core/qa_policy.py))

## Adopt risk-based closure with explicit owner authority

There are three viable policy options. **A button on every card** gives a simple visible gate but forces the owner to click through machine-decidable claims and invites perfunctory approval. **Automatic closure after any AI review** reduces queue size quickly but confuses silence with proof. **Recommended: evidence-gated, risk-based closure** uses a deterministic oracle for low-consequence claims, independent live or human review for partial and subjective claims, and formal sign-off where required. The user should be able to choose a stricter `ask` preference; it is an owner workflow preference, not a claim that every card intrinsically needs a human decision.

For low-risk, reversible, precisely specified work, allow automatic `done` only after a complete current check and a recorded receipt. A verifier must first confirm that the check actually covers the card’s `Done means`; the implementer’s own invented oracle alone should not grant automatic closure. If the check is partial, stale, failing, or blocked by an attributable signal, keep the card open. UI and experiential claims should get an independent staged probe with captured artifact and verdict. Security, privacy, money, deletion, credentials, legal or clinical effects, broad blast radius, contested acceptance criteria, and irreversible external actions require an accountable human decision, plus technical checks. Where the release itself is the acceptance event, keep a separate post-merge or deferred state until release evidence arrives. Canarying and rollback reduce exposure for reversible deployments but cannot prove unobserved behavior safe. ([Google SRE canary guidance](https://sre.google/workbook/canarying-releases/))

**Owner approval in chat is an approval event when it is explicit and specific.** Relay should present the exact card ID, requested transition or external action, evidence summary, known exceptions, and artifact or revision; ask a clear approval question; and bind the owner’s affirmative reply to that scope. Record the owner identity, exact reply, time, card ID, evidence and revision identifiers, decision, executing agent, and resulting receipt in the append-only thread. “Looks good” without an identifiable action, silence, an old approval for a changed artifact, and an agent’s inference are not approvals. An agent may then perform the authorized Board transition without a second UI click, provided the evidence gate and permissions pass. If GitHub requires an eligible approving PR review, use that formal mechanism; the chat reply authorizes execution but does not impersonate the review. A rejected or qualified answer leaves the card open and records the reason.

Exceptions should be explicit rather than hidden in a generic `done`: a product or repository rule can require a formal reviewer; a `Human QA` question needs the owner’s answer; a required sign-off needs its receipt; an unresolved signal blocks departure; unavailable external-world evidence belongs in `deferred` with an owner and trigger; and a knowingly abandoned item goes to `dropped` with a reason. A release gate remains open until release observation. No one should clear these by inserting a bare Verdict heading or by relabeling risk.

## Triage the backlog in measured, reversible phases

**Phase 1: freeze a baseline and inventory without closing cards.** Export IDs, statuses, owners, revisions, commit and evidence links, `Done means`, verify settings, tests, signals, and dependencies to a dated manifest. Reconcile the live count with the 2026-09-24 audit, and identify duplicate or superseded cards without deleting history. Fix malformed metadata separately, preserving original text and an audit entry. Set the effective QA policy deliberately before any batch process. This creates an auditable denominator and prevents a moving queue from being mistaken for progress.

**Phase 2: pilot a small stratified set.** Select cards from each lane and from deterministic, UI, cross-component, high-stakes, and missing-evidence groups. For each, read the original request and current artifact first, rerun relevant tests at the current revision, inspect live behavior where needed, and write an independent verdict before viewing an AI summary. Record minutes spent, missing evidence, actual defects, and reversals. The pilot should calibrate classification rules and effort; the three notes provide no defensible auto-closable percentage for this repository.

**Phase 3: process homogeneous low-risk batches, one claim at a time.** Group cards that share a build or journey so a test run can be reused, but link the exact assertion and result to each card. Close only cards whose full acceptance claim passes their scoped oracle and whose signals and policy gates are clear. Use a predeclared random audit within a genuinely homogeneous class as a check on the gate: preserve the frame and seed, state the sample size and failure threshold, and halt that class for a material miss. Sampling supplements each card’s deterministic gate; it does not close unsampled high-risk cards. Route partial or subjective claims to focused independent probes and owner review. Keep deferred items visible with a concrete trigger and revisit date.

**Phase 4: monitor and roll back.** For each batch, publish counts of closed, verified but awaiting owner, failed, deferred, and dropped cards, along with escapes and reopenings. Retain immutable evidence and thread receipts. A discovered false pass should reopen affected cards, pause the matching closure rule, inspect the whole affected cohort, revise the oracle, and rerun it. For deployed changes, use monitoring and a rehearsed rollback where feasible. Never turn a batch status move into a substitute for checking the underlying artifacts.

## Conclusion

The key design choice is to make **verification a claim about evidence** and **approval a recorded decision by the right authority**. That lets Relay remove needless clicks while preserving a stronger record than a button alone provides. The backlog should shrink only as cards acquire current, scoped proof or an explicit owner disposition; a smaller Board produced by bulk status changes would hide the very uncertainty the queue is meant to expose.
