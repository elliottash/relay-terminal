# Make Relay an editable artifact workspace

*Research synthesis, 23 September 2026.*

**Executive answer.** Relay should build a **local-first editable artifact workspace**: a persistent layout where a person can edit source while an agent works on the same project, with terminals, change review, build output, and a typed preview visible together. ChatGPT's current writing and code blocks, Claude Docs, Gemini Canvas, and Copilot Pages show useful ways to select content and ask for edits, but their documented exports do not establish a live, bidirectional link to local project files. Overleaf shows the strongest integrated TeX experience: source or visual editing beside a compiled PDF, logs, SyncTeX jumps, comments, and tracked changes. Cursor, VS Code, Zed, Codex, Aider, and Replit connect agent requests to local or project files, but differ in when edits hit the working tree and what their review histories capture. Relay can combine their most useful patterns around the files it already opens, while treating an unsaved human buffer and a concurrent agent write as a real conflict to compare or merge, never an implicit overwrite. ([OpenAI writing and code blocks](https://help.openai.com/en/articles/20001246-working-with-writing-blocks-and-code-blocks-in-chatgpt); [Claude Docs](https://support.claude.com/en/articles/16923645-get-started-with-claude-docs); [Overleaf redesigned editor](https://docs.overleaf.com/getting-started/how-do-i-use-overleaf/redesigned-overleaf-editor); [VS Code agent review](https://code.visualstudio.com/docs/agents/run/review-code-edits))

## Cloud canvases make human and AI edits share a document, with different review guarantees

The familiar **ChatGPT Canvas** is a useful interaction reference: its 2024 design put editable writing or code beside chat, supported selection-specific requests, and offered a way back to earlier content. It should be labeled historical in a 2026 comparison. OpenAI says Canvas ceased to be available in GPT-5.5 Instant and Thinking on 28 May 2026, with limited access through legacy models; current writing and code blocks sit inside chat responses. Supported blocks allow direct edits and selected-text requests; code blocks can preview HTML, React, SVG, Mermaid, and Vega or run supported Python. Availability varies by plan, device, model, and rollout. These features save with the conversation; the cited documentation does not establish a continuously synchronized local file. ([OpenAI Canvas launch](https://openai.com/index/introducing-canvas/); [OpenAI model release notes](https://help.openai.com/en/articles/9624314); [OpenAI writing and code blocks](https://help.openai.com/en/articles/20001246-working-with-writing-blocks-and-code-blocks-in-chatgpt))

**Claude Docs beta** is the clearest documented example of a person typing while the AI edits the same cloud document: nothing is locked while Claude works, edits autosave for collaborators, and a comment on selected text can mention `@Claude` to request an anchored change. Claude acts when asked, under the requesting person's permissions, and edits are attributed. Docs export to Word, PDF, Markdown, or Google Docs, but **version history is unavailable** in the beta; Anthropic does not document a same-span conflict algorithm or a live local-file mirror. Claude's template artifacts also allow direct editing and selection-scoped “Edit with Claude,” but artifacts and living Docs are distinct surfaces. ([Claude Docs](https://support.claude.com/en/articles/16923645-get-started-with-claude-docs); [Claude artifacts](https://support.claude.com/en/articles/9487310-what-are-artifacts-and-how-do-i-use-them))

For the **desktop-app question specifically**, OpenAI documents Chat, Work, and Codex in its newer macOS/Windows app, and says Codex works with local files and repositories. Its writing-block guide does not give a platform-by-platform feature matrix, so desktop parity for each block action should be tested rather than assumed. Claude documents Docs creation and editing on web and Desktop; mobile can view Docs but cannot edit them. Claude Code can create a Doc and open it in a desktop side panel. These are cloud Docs, not a documented live mirror of a local `.md` or `.tex` buffer. ([OpenAI desktop migration](https://help.openai.com/en/articles/20001276/); [OpenAI writing and code blocks](https://help.openai.com/en/articles/20001246-working-with-writing-blocks-and-code-blocks-in-chatgpt); [Claude Docs](https://support.claude.com/en/articles/16923645-get-started-with-claude-docs))

Gemini's document Canvas offers direct, autosaved edits, selection-scoped requests, and saved-version controls; its code/app Canvas adds a running preview and recent-changes view. Copilot Pages makes a particularly useful distinction: a localized AI revision can remain a **proposal that the user applies or rejects**. Notion AI offers a similar Accept/Discard/Try again choice in a general page editor whose history can highlight changes. These are interaction precedents for Relay's edit review, not evidence that their cloud documents solve filesystem concurrency. ([Gemini Canvas](https://support.google.com/gemini/answer/16047321?hl=en); [Copilot Pages](https://support.microsoft.com/en-us/microsoft-copilot/using-copilot-pages); [Copilot Page versions](https://support.microsoft.com/en-us/microsoft-365-copilot/view-or-restore-an-earlier-version-of-your-microsoft-365-copilot-page); [Notion AI](https://www.notion.com/help/guides/notion-ai-for-docs); [Notion history](https://www.notion.com/help/duplicate-delete-and-restore-content))

## Overleaf joins TeX source, compilation, PDF navigation, and collaboration

Overleaf's project editor switches between a direct **LaTeX Code Editor** and a Word-like **Visual Editor** over the same project. Its file tree, source pane, Recompile control, typeset PDF, logs, Review, and Chat form a coherent writing environment. Visual editing helps with ordinary prose, images, and some tables, while complex macros and table structures can still require source editing. Collaborators can edit together; Overleaf describes server-side operational transformation and WebSocket updates. Comments attach to selected text or code lines, and premium Track Changes supports accepting or rejecting suggestions. This is more than a PDF viewer, but its rich-text round trip through arbitrary LaTeX is not a sensible prerequisite for Relay's first release. ([Overleaf getting started](https://docs.overleaf.com/getting-started/how-do-i-use-overleaf); [redesigned editor](https://docs.overleaf.com/getting-started/how-do-i-use-overleaf/redesigned-overleaf-editor); [collaboration](https://docs.overleaf.com/collaborating/collaborating-in-overleaf); [track changes](https://docs.overleaf.com/collaborating/track-changes); [tables](https://docs.overleaf.com/writing-and-editing/generating-and-inserting-tables))

For a **two-pane TeX layout**, place editable `.tex`/`.bib` source on one side and the compiled PDF on the other, with Recompile, build status, and an expandable diagnostic drawer in the source header. For a **three-pane layout**, keep the terminal or agent conversation on the left, source in the center, and PDF on the right; let users swap the source and PDF or move logs below. A source cursor should jump to its PDF location, and a PDF double-click should open the matching source file and line. Overleaf uses the PDF's matching `output.synctex.gz` for these jumps, and notes that stale builds and line-level mapping limit accuracy. Relay should retain page and zoom across refreshes and label the PDF stale when the source has changed since its last successful compile. ([Overleaf PDF/source navigation](https://docs.overleaf.com/navigating-in-the-editor/working-with-the-pdf-viewer/moving-between-the-editor-and-pdf); [Overleaf layout](https://docs.overleaf.com/navigating-in-the-editor/working-with-the-pdf-viewer/editor-and-pdf-layout-and-sizing); [TeXstudio viewer](https://texstudio-org.github.io/viewing.html))

The local build loop should select a main document, engine, output directory, and visible command; use `latexmk` as the compatibility-oriented default where available; watch included sources, bibliography, images, and configuration; debounce changes; run compilation off the UI thread; parse file-and-line errors into clickable diagnostics; and publish a PDF together with its SyncTeX map only after the same build generation completes. Retain the last successful PDF when a build fails, labeled with its source revision and failure state. Overleaf itself uses `latexmk` and project `latexmkrc`; local editors such as LaTeX Workshop and TeXstudio demonstrate configurable recipes and internal SyncTeX-aware PDF viewing. This build-generation design is a Relay recommendation, not a description of Overleaf's internal scheduler. ([Overleaf recompiling](https://docs.overleaf.com/getting-started/recompiling-your-project); [Overleaf latexmkrc](https://docs.overleaf.com/managing-projects-and-files/the-latexmkrc-file); [LaTeX Workshop compile](https://github.com/James-Yu/LaTeX-Workshop/wiki/Compile); [LaTeX Workshop view](https://github.com/James-Yu/LaTeX-Workshop/wiki/View))

Overleaf's **premium Git remote** can connect a local checkout to an online project through explicit pull and push, but it is a linear `master` branch translation of Overleaf history. Its GitHub synchronization is manual, and Overleaf warns that pulling can disturb comments and tracked changes. Relay should therefore offer optional, deliberate Git synchronization with visible diffs and conflicts; it should not present Git as live Overleaf coediting or promise to preserve online review metadata. The cited Overleaf documentation does not establish a public integration for collaborator cursors, comments, or build results. ([Overleaf Git integration](https://docs.overleaf.com/integrations-and-add-ons/git-integration-and-github-synchronization/git-integration); [advanced Git operations](https://docs.overleaf.com/integrations-and-add-ons/git-integration-and-github-synchronization/git-integration/advanced-git-operations); [GitHub synchronization](https://docs.overleaf.com/integrations-and-add-ons/git-integration-and-github-synchronization/github-synchronization))

Offer two saved three-pane presets: **equal columns** `Terminal | TeX | PDF`, and the proposed **large-PDF layout**, with TeX above Terminal in the left column and PDF filling the right column (initial width ratio 1:2, user-resizable). In both, the terminal composer should say which document or project it is linked to, so a request like “tighten this paragraph” has a visible target. A selection in TeX should travel with the request as a file, range, and source revision rather than only pasted text.

## Terminal agents prove the need for a shared view and an honest change record

Cursor, VS Code/Copilot, Zed, Codex, Claude Code's VS Code extension, Aider, and Replit all connect an editable project to agent requests, but they make different tradeoffs. Cursor lets an agent edit files and run commands while a review UI exposes selective acceptance. VS Code's Agent Host can write into a folder or isolated worktree and shows Files and Changes beside chat; its own documentation says the Changes list **omits files modified only through terminal commands**. Zed's Agent Panel offers multi-buffer diffs and recommends worktrees when independent agents could touch the same files. Codex's IDE extension lets people edit local code and preview changes; Replit gives movable Editor, Agent, Preview, Console, and Shell tabs, and isolated background tasks reach a reviewable apply boundary. Aider watches saved source comments as requests, which is a useful lightweight bridge between an external editor and a terminal agent. ([Cursor agent](https://docs.cursor.com/agent); [Cursor review](https://docs.cursor.com/en/agent/review); [VS Code review](https://code.visualstudio.com/docs/agents/run/review-code-edits); [Zed Agent Panel](https://zed.dev/docs/ai/agent-panel); [Zed parallel agents](https://zed.dev/docs/ai/parallel-agents); [Codex upgrades](https://openai.com/index/introducing-upgrades-to-codex/); [Claude Code extension](https://marketplace.visualstudio.com/items?itemName=anthropic.claude-code); [Replit editor](https://docs.replit.com/features/editor/editor-and-tools); [Replit task board](https://docs.replit.com/features/agent/task-board); [Aider watch mode](https://aider.chat/docs/usage/watch.html))

**Simultaneous editing needs explicit local rules.** A watcher can report that the disk changed; it cannot safely merge an unsaved human buffer with an agent's write. Relay should store the buffer's last loaded content hash and compare it with disk before saving. If the buffer is clean, reload an external change while preserving cursor and view state. If it is dirty, preserve both versions, show a three-way comparison against the loaded base, and offer merge, reload, or save-as. Renames, deletes, and binary replacements need explicit states. Agent-produced patches can be previewed and accepted by hunk when practical; for a long or overlapping run, give the agent an isolated worktree and an apply/merge step. Record **all observed file changes**, including terminal and external-editor writes, in a workspace change view; identify an actor or command only when Relay has evidence, rather than labeling every write as an agent edit. These are proposed Relay semantics, since the cited products do not document a universal merge protocol for concurrent unsaved buffers. ([VS Code review](https://code.visualstudio.com/docs/agents/run/review-code-edits); [Zed parallel agents](https://zed.dev/docs/ai/parallel-agents); [Zed Project Panel](https://zed.dev/docs/project-panel); [Replit task board](https://docs.replit.com/features/agent/task-board))

For a **Relay-native agent**, make the open editor buffer the edit target: send it a revision-aware patch, show the proposed diff in the document, and apply non-overlapping hunks without replacing text the person typed while the request ran. If a patch overlaps newer human edits, pause that hunk for review while leaving the rest of the document editable. Guest agents and shell commands will still write files on disk; their changes enter through the watcher and the same comparison path. This separates shared editing from periodic full-file reloads.

## Build one artifact workspace that can host source, execution, and spatial previews

Relay's starting point is concrete. [`FilePreview`](../src/FilePanes.h) already opens local text and Markdown for editing, saves local text atomically with `QSaveFile`, edits SSH-hosted text with a changed-file conflict choice, and renders Markdown, images, and PDFs when Qt PDF is present. [`RelayWindow::openPath`](../src/RelayWindow.h) already places and reuses file panes beside other panes. [`README`](../README.md) documents the split-pane and file-pane model. The current local save path does not compare the disk file with the loaded revision, and `FilePanes` has no `QFileSystemWatcher`; [`PlanEditor`](../src/FilePanes.cpp) is a separate editor. Qt PDF is an optional build component, so a packaged workflow needs to check viewer availability and offer an explicit fallback. These are code observations as of this report, not promised features. ([Relay file panes](../src/FilePanes.cpp); [Relay build configuration](../CMakeLists.txt))

The broad feature should be **workspace-aware editable artifacts**, not a TeX-only mode. Give each workspace a root, saved pane layout, open buffers, running terminals/agent threads, change view, and artifact definitions that connect **source → command or renderer → output → viewer**. A text file can pair with Markdown/HTML or PDF; a script with a terminal, diagnostics, plot, table, or notebook-like output; an image or artwork file with a canvas and layers/properties from a suitable editor; a diagram with source and rendered graph; CAD code or model data with a 3D view and an explicit regenerate/commit boundary. The viewer should say **live, building, stale, or failed**, show which source revision produced it, and expose format-specific navigation. JupyterLab and Posit show persistent layouts with source, consoles, outputs, and previews; Blender and Onshape show why scripts and geometry often need explicit Run or Commit rather than a generic text preview. For a visual editor, Relay must declare which representation is authoritative and which manual changes survive regeneration. ([JupyterLab interface](https://jupyterlab.readthedocs.io/en/stable/user/interface.html); [Posit pane layout](https://docs.posit.co/ide/user/ide/guide/ui/ui-panes.html); [Posit Quarto](https://docs.posit.co/ide/user/ide/guide/documents/quarto-project.html); [Blender editors](https://docs.blender.org/manual/en/latest/editors/index.html); [Onshape Feature Studios](https://cad.onshape.com/help/Content/FeatureStudio/feature_studios.htm); [draw.io Mermaid update](https://www.drawio.com/blog/mermaid-updates/))

**Implementation order:** first, make the current editor a safe shared-file surface through local and SSH change observation, revision-aware saves, compare/merge UI, saved layouts, and a complete filesystem change view. Second, deliver a TeX/Quarto-style artifact runner with configurable commands, incremental rebuilds, diagnostics, PDF refresh, and matching SyncTeX navigation; the two- and three-pane layouts then become usable end-to-end. Third, add a typed preview interface for scripts, diagrams, artwork, and CAD, plus reviewable agent patches and optional worktree isolation for competing edits. For remote projects, run build tools beside the source and carry the PDF, SyncTeX map, diagnostics, and source revision back as one generation. This sequence builds on Relay's existing pane system while making concurrent writes and output freshness reliable before expanding the number of artifact types. ([Qt PDF](https://doc.qt.io/qt-6/qtpdf-index.html); [LaTeX Workshop view](https://github.com/James-Yu/LaTeX-Workshop/wiki/View); [Zed parallel agents](https://zed.dev/docs/ai/parallel-agents))

## Conclusion

The decisive product boundary is **ownership of the working artifact**. Cloud canvases make AI requests easy inside their documents; Overleaf makes TeX compilation and collaboration unusually cohesive; agent IDEs operate on project files but expose uneven histories of what actually changed. Relay can offer one dependable local workspace across all three concerns by treating files, unsaved buffers, agent writes, build generations, and typed outputs as linked states. That would let a person keep writing while an agent edits, then see exactly what changed and whether the preview still represents the current source.
