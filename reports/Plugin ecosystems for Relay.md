# Plugin ecosystems for Relay

Research snapshot: 23 September 2026. This compares documented extension mechanisms and public catalogs, then checks Relay's current code. Catalog entries are **availability**, not installation counts or usage rankings. The local check below inspected names and counts only; no credentials or personal configuration values were copied into this report.

## The same word covers two different products

Warp, Claude, and Codex mostly use extensions to give an **agent** instructions, tools, or automation. The proposed Relay document and statistical plugins also change the **workspace**: which language the composer runs, which process owns state, which panes appear, and how output is rendered. Relay needs both layers, but they should have different interfaces. A generic GitHub MCP server should be reusable in any workspace; a TeX workspace must own its editor/build/PDF relationship. This is a design inference from the product documents and [Relay's task-workspace scope](../issues/design/2026-09-23-task-plugins-a-workspace-kind-adds-a-language-ro.md).

The [Anthropic-maintained marketplace manifest](https://github.com/anthropics/claude-plugins-official/blob/main/.claude-plugin/marketplace.json) contained 311 entries when checked. Its largest labeled groups were development (123), productivity (66), database (39), monitoring (22), and security (18). These counts describe one current catalog, **not popularity**. On this machine, a read-only inventory found many standalone skill files and only a few installed plugin bundles. Plugin cache directories were excluded from the installed count because cached packages can be merely available.

## Relay's present boundary

Relay's native worker indexes Warp-style SKILL.md files and offers load/read tools; its Skills dialog can exclude, refine, import and check updates. The documented default is `~/.warp/skills`, while guests also receive Relay's injected skill catalog. [Architecture § Skills](../docs/ARCHITECTURE.md), [guest tool mapping](../docs/GUEST-TOOLS.md). Relay bridges Board and app tools **outward** to Claude/Codex guests over MCP in [guest_board_bridge.py](../backend/relay_core/guest_board_bridge.py). This checkout has no corresponding general MCP **client** that a native Relay agent can use to discover and call a third-party server; the current deferred tool groups are fixed in [tool_groups.py](../backend/relay_core/tool_groups.py). That is a code observation as of this snapshot.

Relay also has file panes, including text editing and optional PDF viewing, but no package format that declares a task workspace's router, runner, layout, previews and tool dependencies. See [the workspace research](Editable%20workspaces%20for%20Relay.md) and [#MEPR](../issues/design/2026-09-23-task-plugins-a-workspace-kind-adds-a-language-ro.md).

## What to build, in dependency order

1. **Keep skills portable.** Continue reading SKILL.md directly. Add clear user/project scope, namespace collision handling, enable/disable state and provenance in the catalog. Import a Claude or Codex skill as a skill; do not require its full plugin to run. The existing Skills dialog is the base.
2. **Add a native MCP client.** Support local stdio and remote Streamable HTTP first, with tool/resource discovery, connection status, per-project enablement, OAuth or secret references, bounded output, and lazy tool schemas so large servers do not fill every prompt. A cloned repo's server definition must not silently execute. Make the same connected tools available to native Relay agents and to guests through a deliberate bridge, without duplicating credentials. This is the main interoperability gap: GitHub, Figma, Linear, Sentry, databases and similar services can then use existing servers. Warp's [file-based MCP safeguards](https://docs.warp.dev/agents/capabilities/mcp/) and Claude's [install summary](https://code.claude.com/docs/en/discover-plugins) are useful UX references.
3. **Define Relay task workspace packages.** A versioned local manifest should declare activation rules, composer language/routing, a runner or persistent kernel, agent tools/skills, pane roles/layout, preview types and output freshness. Keep execution and UI APIs explicit. The first two packages should be TeX→PDF and Python/Stata, as scoped in [#MEPR](../issues/design/2026-09-23-task-plugins-a-workspace-kind-adds-a-language-ro.md); both depend on safe shared editing in [#P2W8](../issues/features/2026-09-23-editable-artifact-workspace-linked-editor-termin.md).
4. **Add code intelligence and lifecycle events where tasks need them.** LSP navigation/diagnostics belong in the programming workspace; LaTeX diagnostics and SyncTeX are document-specific. After the basic package format is stable, add a small, named event API for on-save/build/preview and optional monitors. Claude's plugin format shows these can be packaged, but Relay should avoid loading arbitrary hooks simply because it recognizes another product's manifest. [Claude plugin components](https://code.claude.com/docs/en/plugins).
5. **Distribute only after local packages work.** A curated built-in catalog and project-local manifests are enough for the first release. Later, support signed or pinned third-party sources, dependency and permission summaries, update controls, and compatibility importers for selected Claude/Codex bundles. Neither format is automatically a Relay workspace: their manifests describe agent extensions, and their UI/hook contracts are host-specific. [Claude marketplaces](https://code.claude.com/docs/en/discover-plugins), [Codex packaging](https://developers.openai.com/plugins/build/plugins).

**First vertical slice:** open a `.tex` project as a linked editor/terminal/PDF workspace, invoke `latexmk`, show a build status and clickable diagnostic, and keep a human edit safe while the agent edits the same file. Then reuse the package contract for a Python kernel with `run_cell`, variables and plots; add Stata through the bridge validated on the owner's installed Stata version. The common package contract should be judged by whether the second workspace requires little core UI code.

## Decisions that matter before implementation

- **MCP runtime ownership:** one connection per tab/workspace or a shared process with scoped credentials and calls. Prefer a shared connection manager with per-workspace grants, unless kernel state or server isolation demands otherwise.
- **Plugin compatibility:** import skills and MCP definitions first; show unsupported hooks, LSP and UI components explicitly. Avoid claiming that arbitrary Claude/Codex plugins work unchanged.
- **UI scope:** start with Relay-native panes and previews. Consider MCP UI resources only after the editor/preview contract is stable.
- **Research limit:** neither marketplace listings nor this machine's installed set reveal population-wide usage. A later adoption study would need download, active-use or survey data supplied by the vendors.
