# Bundled skills for Relay

Research snapshot: 24 September 2026, for [#SZ1H](../issues/design/2026-09-24-bundled-skills-what-ships-with-relay-today-what.md). It reads the concept of a skill from [#1QKM](../issues/design/2026-09-23-cards-build-servers-servers-serve-cases-skills-a.md), surveys what Warp, Claude Code, Codex, VS Code, Cursor, Gemini CLI, Kiro and OpenCode bundle and how they show it, measures what Relay's catalogue does on the owner's machine today, and ends with a recommendation on each of the card's four questions plus the starter-task question from [#9HS0](../issues/design/2026-09-24-beginner-ux-and-onboarding-a-start-pane-with-sta.md). Vendor claims are from the pages linked; local numbers were measured by loading Relay's own `SkillIndex` in this checkout. Nothing here is decided.

## 1. What a skill is, read from #1QKM

#1QKM's vocabulary: a **card** builds a **server**; a server serves **cases**; a **program** serves a case by algorithm and a **skill** serves it by reasoning. Four properties of a skill follow from that and each one bears on bundling.

- **A skill is a server, so it has a version and a track record.** Relay already computes both: `cases.skill_version` hashes the manifest, and `skills_list` carries `cases`, `pass_rate_30` and `stale` from the board's ledger (#95VZ). A bundled skill is therefore not "a Markdown file we ship" but a server Relay puts on every machine and vouches for. It needs what a shipped program needs: a declared environment, a test that runs at release, and a way to say "this one is broken here".
- **A skill fails plausibly, so it earns authority per case.** #1QKM §1 and the QA ladder (#BX7B) put the human-QA designation on the server and let it fall with the record. For bundled skills the record is Relay's, not the user's: the first run on a new machine has no cases. So a bundled skill must arrive with its own evidence (a `Try it` case, an eval) rather than start at zero, or its profile must say `human: required` until the local record exists.
- **Rot rate is a profile factor (§7), and it is the one that decides what may be bundled.** A skill that drives an external UI (Editorial Manager, Beam, Amazon) rots in weeks; a skill that operates Relay itself or local programs rots when Relay changes, which Relay controls. Everything Relay bundles today is low-rot for that reason. A mail skill over the Gmail API is medium-rot and credentialed; a mail skill over a browser is high-rot. This ranks the starter-task candidates by whether Relay can keep the promise.
- **The codification axis runs inside a server (§2).** A skill's credential handling, its login, its API calls are algorithmic steps; the judgement ("which of these threads needs a reply") is the intelligent step. So "a mail skill with a credential story" is really a program (a tool group that owns the credential, like a task plugin's runner) plus a skill that uses it. That is how the two bundled workspace skills already work: `python-workspace` is a thin skill over the `py_*` tools that `relay.python` provides, and the plugin, not the skill, declares `requires`.

Two more consequences. A **starter task is a case template, not a skill**: it names the server that would serve it, stages a first prompt, and checks the server's requirements; that is exactly the recipe shape #9HS0 chose ("layout, a first prompt staged in the composer, a one-line needs check"). And the **catalogue is the lookup from case to server**: a duplicate entry is the same server at two versions, and an entry whose tools are absent is a server that cannot serve here. Both are catalogue-quality problems with server-level answers (identity, requirements), not string-matching answers.

Across tools, the [Agent Skills specification](https://agentskills.io/specification) is the shared floor: `name` (matches the folder), `description` up to 1,024 characters, optional `license`, `compatibility` (up to 500 characters of free-text environment requirements), `metadata` (string to string) and experimental `allowed-tools`; metadata of about 100 tokens per skill at startup, the body when activated, files on demand. Cross-tool installers exist: Vercel's `npx skills add` writes a skill into seventy-odd agents' directories and reports installs to the `skills.sh` leaderboard; Anthropic's marketplace manifest held 311 plugins when [the plugin report](Plugin%20ecosystems%20for%20Relay.md) counted it.

Nine patterns that matter for #SZ1H:

1. **Everyone bundles a small operating set and nobody bundles job skills.** Claude ships about ten, Cursor about fifteen, Warp fourteen plus eight, Codex a handful; every one is about running, verifying, reviewing, planning, configuring the product, or making more skills. Document and mail skills come by account sync, plugin or marketplace. Relay's three bundled skills plus the plugin-carried workspace skills are the same shape.
2. **The product bundle is a set the user can switch off and that loses every conflict.** `disableBundledSkills`, Codex system last, Gemini extensions lowest and prefixed, Cursor's "managed" label. Relay's bundled directory is already last in the search order; it has no set-level switch or label.
3. **Requirements exist in three forms and nobody checks programs.** Free text (`compatibility`), a structured MCP dependency (Codex `dependencies.tools[]`), or shipping the dependency inside the package (Kiro powers, Gemini extensions with declared `settings` for keys). Relay's task-plugin `requires` (program, alternatives, version flag, install hint, optional), checked before activation, is ahead of all of them; skills simply do not have it yet.
4. **Availability is gated by tools, not by name.** Warp puts MCP-dependent skills under `mcp_skills/<server>/` so they only make sense where that server is configured; Kiro activates by context; Claude gates by `paths`. A name list like `DEFAULT_EXCLUDE` is what nobody does.
5. **Nobody dedupes by content.** Claude namespaces the copies; the rest let the first directory win. Claude's synced `manifest.json` does carry `skillId`, `source` and `updatedAt`, so provenance exists to read.
6. **The model-facing line and the human-facing line are different fields.** Codex's `short_description` (25 to 64 characters, for chips) sits beside the model's `description`; Relay's `short:` is the same idea, but only Relay's own skills set it.
7. **Invocation policy is a first-class switch.** `disable-model-invocation`, `user-invocable`, `allow_implicit_invocation`, `permission.skill` allow/deny/ask. Relay has exclusion only; a skill that pays rent is listed for implicit use like one that formats a commit.
8. **A "make a skill" skill ships everywhere** (`skill-creator`, `create-skill`, `/run-skill-generator`), and the newest ones carry evals. Relay has refine and import but no bundled skill that writes a skill with a profile and a `Try it` case.
9. **Catalogue budgets are bigger than Relay's.** Codex allows 8,000 characters; Claude 1,536 per skill; Relay's whole section is 5 KiB.

## 3. Relay's catalogue on the owner's machine, measured

Loading `default_directories(workspace)` with `DEFAULT_EXCLUDE` in this checkout:

| Measure | Value |
|---|---|
| Skills listed | 61 |
| From the owner's Warp user tree | 30 |
| From Warp's product bundle (`remote-server/bundled_resources`) | 15 |
| From Claude's synced account skills | 13 |
| Relay bundled | 3 |
| Skipped lines reported | 34, of which 24 are the same eight synced skills three times over (four synced folders hold the same set) |
| Trigger length the prompt section settled on | 50 characters (`MAX_SHORT` is 100; 61 lines do not fit in 5 KiB) |
| Prompt section size | 4,463 bytes |
| Guest catalogue (`[Relay skills]` block) | one JSON row per skill, 240-character trigger plus the absolute `SKILL.md` path |

Read by hand against what each `SKILL.md` needs, the 61 fall into three groups. About a third name a tool Relay does not have: the eight Figma skills (Figma MCP), `built-in-browser`, `chrome-browser`, `computer-use`, `docs`, `import-memory`, `morning` (Claude desktop and claude.ai surfaces), `pr-comments` (Warp's `insert_code_review_comments`), `factory-files`, `tui-migrate-setup`, `change-keybinding`, `tab-configs` (Warp's UI and files), `provenance` (a kernel MCP). About a quarter need a credential or a local install the manifest does not declare: `beam-rent` (Brave profile and Playwright), `email-triage` (Gmail API), the three `jle-*` and `editing-send-for-review` (Editorial Manager), `openreview-ac`, `subscription-manager`, `rclone-dropbox-sync`, `paper-sharing`, and the four document skills (Python libraries behind their scripts). The rest, about 26, are portable procedures that work anywhere: `deliver`, `clean-commit`, `code-cleanup`, `documentation`, `tests`, the referee and editing skills that only read a PDF, `deep-research`, `two-dimensional-slide-deck`, and so on.

Two things follow. At 50 characters every trigger on this machine is cut before the words that say when to use it, so the model chooses among 61 lines that mostly read as titles; and 21 of those lines are for skills that cannot run here. Hiding the unrunnable ones alone would let the remaining 40 have 70-character lines under the current budget; 8 KiB would give them the full 100. On a Claude guest the `[Relay skills]` block also repeats the 13 synced skills the harness already lists under its own `anthropic-skills:` names, which is the doubled catalogue the card observed.

## 4. Recommendations

**Q1. Which skills ship.** Keep the bundle to skills whose tools Relay itself provides, which is the operating set every product ships. Bundle: `deliver`, `guest-account-setup`, `local-model-setup`, the plugin-carried workspace skills, and one addition, a Relay `skill-creator` that writes a skill with a `profile:`, a `requires:` and a `Try it` case (pattern 8; it also retires the `create-skill` versus `skill-creator` duplicate for Relay's purposes). Do not bundle a skill that drives another product's UI or holds a credential story Relay does not own. For the starter tasks: the eleven recipes are case templates and ship as #9HS0 decided; *mail* and *subscriptions* say "needs a skill" until Relay owns the program half. The honest route to a bundled mail skill is a mail **task plugin** (a `mail_*` tool group over IMAP or the Gmail API with the credential in Relay's keystore, `requires` on the plugin) and a thin bundled `email-triage` skill over it, the way `python-workspace` sits over `relay.python`. That is a design card of its own and an owner decision on scope.

**Q2. Identity and hiding.** Dedupe by content, not only by name: `cases.skill_version` already hashes a manifest, so two folders with the same hash are one server and the catalogue shows it once with the other paths as "same as"; same name with different content keeps first-directory-wins but records the shadowed version. Hide by tool availability rather than by name: a skill whose declared `requires` names a tool group or MCP tool the pane does not have is not listed (it cannot serve here), and the Skills dialog shows it greyed with the reason. Absent a declaration, two cheap inferences cover today's catalogue: a Warp skill under `mcp_skills/<server>/` needs that server, and a synced Claude skill whose description names `mcp__<server>__*` tools needs those. Two defaults change: Warp's `remote-server/bundled_resources` tree stops being discovered by default (it is Warp's product bundle, the counterpart of Claude's built-ins, which Relay does not read either; `~/.warp/skills` and the owner's `_Agents/.warp/skills` stay), which removes `DEFAULT_EXCLUDE`'s reason to exist; and the guest catalogue omits skills under the guest's own home tree (`~/.claude/skills` for a Claude guest, `~/.codex` and `~/.agents` for Codex) because the harness lists those itself and the block is described as a supplement.

**Q3. A `requires` on skills.** Yes, in the task plugin's shape so one checker serves both: `program` (with `alternatives`, `version_arg`, `install_hint`, `optional`), plus `env` (a variable that must be set), `secret` (a keystore entry) and `tool` (a Relay tool group, `py`, `tex`, `board`, or an MCP tool pattern). Written as a `requires: |` block of `key: value` lines, the same trick `profile: |` uses so the flat frontmatter parser needs no change and the file stays valid under the spec. Checked at index time, which costs a `which` and an environment lookup per skill: a missing *tool* hides the skill; a missing *program* or *secret* keeps it listed with "needs X" on the `skills_list` item and, for the catalogue line, a trailing "(needs rclone)" so the model can say so before the first failed run. The spec's free-text `compatibility` is read and shown, never checked. The profile's `money: yes` or `sign_off: send` should also set the invocation policy (pattern 7): such a skill is listed for the user to invoke by name and never chosen implicitly; that is a two-line rule once `requires` lands and it answers the rent-payment case without a new field.

**Q4. The catalogue line.** Use `short:` when present, otherwise the first sentence of the description, which `_clip` already prefers when the sentence ends past two thirds of the limit; the fix is the budget and the population, not the clipper. Raise `MAX_PROMPT_BYTES` to 8 KiB (Codex's figure) and let hiding unrunnable skills do the rest; keep the "shorten every line together" rule for libraries that still overflow, since it is the right behaviour. For the guest block, drop the absolute path from each row when the guest can find the skill by name, or keep it only for skills outside the guest's own discovery.

**Bundled skills as servers.** Every bundled skill gets a `profile:` (only `deliver` has one), a `requires:`, a `Try it` case that `board_try` can run, and a release test `tests/test_bundled_skills.py`: each manifest parses clean, has `short`, its profile warns nothing, every file it references exists, and its `requires` are either satisfied in CI or marked optional. That is the "program-shaped QA" #1QKM says a shipped server needs, and it is what none of the surveyed products do for their bundles.

## 5. Suggested delivery, for the owner to file

1. **Skill `requires`, tool-availability hiding, content-hash identity** (worker, medium): `skills.py`, `skill_manage.py`, the two default changes in Q2, tests in `tests/test_skills.py`.
2. **Catalogue line and budget** (worker, small): `short:` else first sentence, 8 KiB, guest block without the harness's own tree.
3. **The bundle as servers** (worker, medium): profiles and `requires` on the three bundled skills and the two workspace skills, a Relay `skill-creator`, `Try it` cases, `tests/test_bundled_skills.py`.
4. **Mail as a task plugin plus a bundled skill** (design, large): owner decision on scope and provider; unblocks the "needs a skill" line on two starter tasks.
