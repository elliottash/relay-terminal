**Adopt: these catch real defects in my plan.**
1. **The human checkout and a moving `main`.** My plan had the queue fast-forward `refs/heads/main` while `~/repos/relay-terminal` has `main` checked out. Its files and index would not move, so `git status` there would show every landing as reversed, and a plain commit from it would revert them. That is the 09-18 bug again, in a new place. GPT-6's fix is right: at cutover the human checkout moves to its own branch, and it is refreshed only by an explicit clean-tree sync.
2. **`board-sync` is a second writer of `main`.** I had `.board/` "landed by the backend on its own", which is exactly a second writer. Board snapshots have to go through the same publisher as metadata jobs.
3. **The queue never rebases the author's branch.** It builds a candidate in a workspace it owns. My background-rebase step D rewrote live branches. Deferring it in favour of main-moved notices plus an explicit sync under a lease is correct.
4. **Immutable submissions**: a committed SHA, idempotent, with a receipt. Intent is persisted before publishing, and restart recovery checks the ref before retrying. Uncommitted work never goes in.
5. **Processes cannot move directory.** A workspace has to be allocated before the shell, guest or tools start. An existing pane can migrate only at a stopped turn.
6. **A policy change cannot approve itself**; a docs-only fast lane still gets its checks; a Python-only change still runs Python checks.
7. **Terminology and sizing.** Sparse checkout that excludes paths is not cone mode (it needs non-cone patterns or a directory-level listing). Verification uses the full tree. A missing `.board/` in a workspace must never create a second Board. The 57 GB figure grows with session count, so it is an estimate, not a bound.
8. **A clean tree can hold unlanded commits.** Garbage collection needs a publication receipt, not just `git status` being clean.
9. **Reconciler replay should be scored against independent acceptance tests, not historical landed text.** 8 of this week's landings were themselves wrong.

Owner, 2026-09-26, Q10: "i want a runnable build on main, is the cost acceptable?" Yes, recorded as a requirement: the queue keeps a runnable build of the latest `main` for the owner.

Design: it is the queue's own **warm tip build**, which the plan already needs as the incremental base for verification. It is a service-owned tree at `$XDG_STATE_HOME/relay/integration/<repo>/tip/{src,build}` with the same slot layout and flags as the verify slots, so every compile is a ccache hit on what the landing's verify just compiled. After each publication it builds target `relay` only, coalesced: at most one rebuild in flight, and later landings fold into the next one. It then installs to `…/tip/run/<sha12>/` and flips a `current` symlink, keeping the last two, so a running Relay is never rebuilt underneath. A launcher entry ("Relay (main)") runs `current`.

Cost measured here: source ~40 MB (sparse; qa evidence is not needed to run), build dir ~3.7 GB, two installed binaries ~0.5 GB. That is **≈4–5 GB of disk**. CPU is roughly one link per coalesced update (relay is 243 MB with debug info), about 10–40 s, and no extra compiles. At 86–225 C++ landings a day that is under ~2 CPU-hours a day, less with coalescing. Accepted.

Separate fix found while answering: `cmake/CompilerCache.cmake` rewrote `ccache.conf` to `max_size = 10G` on every configure. The 40 GB raise was already undone within the hour. `1d468dc7` makes a configure never lower a larger cap (tests/test_compiler_cache.py 8 passed), and the cap is back at 40G.
