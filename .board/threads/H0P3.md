Assessment (Claude Fable, 2026-09-24). The persistence the owner asks for is already the design: a pinned key pair on each side, a device record in `devices.json` on the desktop and in IndexedDB on the phone, a per-device connect token, always-on registration, and reconnect on `visibilitychange` / `pageshow` / `online`. Re-pairing is a symptom of two faults (#Q5QJ two hubs fighting over one identity; #SAW4 the phone landing on the pairing form when its record read stalls), not of a missing account layer. Fix those first; then decide here whether the phone's identity should survive storage loss.

Options, once the bugs are fixed:

**A. Nothing new.** A PWA's socket dies seconds after the screen locks; iOS gives no background socket to a web app. "Persistent" therefore means instant re-attach on wake plus Web Push while asleep, which is what is built. Cost: none. Risk: a wiped IndexedDB (Safari's 7-day eviction for a non-installed tab, a phone restore) still means a QR and a click on the desktop.

**B. Passkey-derived device key (recommended).** Register a WebAuthn passkey for join.relay-terminal.ai on the phone and derive the X25519 private key from the PRF extension output (iOS 18+, Android/Chrome). The key is then a function of Face ID + the passkey in iCloud Keychain: a wiped IndexedDB, a reinstalled app or a new iPhone regenerates the same device key, the desktop's pinned record still matches, and no server ever holds a key. The rendezvous is the relying party and stores only credential public keys. The desktop still confirms a device once; there is no second pairing after that. Cost: a few days; needs a fallback for phones without PRF (today's flow).

**C. An account on relay-terminal.ai.** Sign-in (passkey or email link) gives a signed device registry: the desktop trusts device keys the account has signed, so a new phone attaches after sign-in plus one desktop confirmation, and a desktop whose identity key is lost can be re-endorsed instead of every phone re-pairing. The server sees account, device and desktop identifiers, never content. Cost: weeks (accounts, recovery, revocation, abuse, ToS). Worth it when there are several desktops or shared teams, not for one phone and one desktop.

**D. Native shell (Capacitor, the #PH0N "Phase 4" option).** Keychain-backed keys survive everything the OS allows and reconnects can run in a short background window; still no permanent socket on iOS. Cost: an App Store presence.

Recommendation: land #Q5QJ and #SAW4 this week, run the owner's phone for two days, then do B. C only if multi-desktop or team use makes the registry worth its own service.

Question for the owner: after the two bugs are fixed, do you want B (passkey-derived key, no account) or C (account)? Recommendation: B.
