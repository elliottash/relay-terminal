**Short answer: much less than when it was filed.** The benefits the card listed have mostly been absorbed by what shipped since 2026-09-17:

| Card's promise | What covers it now |
|---|---|
| Works over SSH, in any terminal | Pane shells wrap `ssh`/`mosh` natively — persistent remote panes, remote splits, remote file previews, agent workers running on the far host (`docs/SSH-AND-MOSH.md`, cards #XQ8F, #SPBN, #A6SH) |
| Reach Relay from a machine without the GUI | The remote protocol + phone/web view and the guest-CLI bridge (`docs/REMOTE-AND-MULTIPLAYER-DESIGN.md`) |
| Shell pane + routed prompt + inline agent output | That's the core Qt pane, already working against remote hosts |
| Same backend worker | True, and the worker protocol is documented — so a TUI would be *cheaper* than estimated, just less needed |

What's genuinely left is one niche: **you're sitting at a bare terminal with no way to run Qt at all** (a headless box you're ssh'd into from a minimal console) and want the Relay composer *there*. But the shipped topology answers that from the other side — run the Qt app where the display is and push panes to the remote host — which is the better architecture anyway (one GUI codebase instead of two frontends).

Also worth noting: the research doc assumed KonsolePart; since KonsolePart was retired for Relay's own engine, a TUI would now duplicate *more* of the frontend (screen model, scrollback, selection), raising the real cost above the 4–6 week estimate.

My recommendation: close it `dropped` / `obsolete`, or leave it in Deferred with a note that SSH panes and the remote protocol covered the motivation. Want me to close it, or park it?
