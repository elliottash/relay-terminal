Review follow-up landed on `main` (2026-09-19). Seven findings from the review of the chord fixed
in one commit:
- The drag hint named the move **away** from the drop anchor (a pane dropped from the anchor's
  right was taught "Move-right then Move-down"). The two sides are swapped, and the decision is
  now `relay::panes::moveToward()` with a test.
- The chord could fire in a tab the user had left: `dockBeneathNeighbor()` now requires the page
  to be the current tab, the `QTabWidget::currentChanged` handler closes the window, and so does
  a scroll (`QEvent::Wheel`), which is how the tab bar changes tabs with the mouse.
- The arming text was a raw `showPaneToast` on every left/right move, outside the hint registry.
  It goes through `hint("pane.dockBeneath.chord", …)` now, so it respects the show limit and the
  "Shortcut hints" setting (WARP.md standing rule).
- The chord and the placement window (#78BN) shared one label and neither ended the other:
  `armBeneathDock()` calls `endPlacement()`, `armPlacement()` calls `endBeneathDock()`, and the
  chord no longer deletes the placement label.
- `dockBeneathNeighbor()` could return after a successful `takeLeaf()` with the pane detached and
  the caller would then run a plain Move-down on it. Everything is validated before the detach,
  and after it the pane is always re-inserted.
- Any modified key kept the window armed, so Ctrl+C / Ctrl+D / Ctrl+L typed at the shell left a
  stale chord. The window now survives only a bare modifier and the keys the keymap binds to
  Move-left/right/down (`relay::panes::chordKeyKeepsWindow()`, tested).
- `docs/KEYBINDING-PRESETS.md` now says the Warp preset binds none of the three move actions, so
  the chord is out of reach under it; the evidence `notes.md` records that screenshot 10's hint
  text is the bug, not the fixed behaviour.
