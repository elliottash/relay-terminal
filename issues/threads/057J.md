spark, Xvfb, fresh profile, before = the clean export of ccb31a8e:
one idle pane 0.48 % -> 0.33 % CPU and 325 -> 162 syscalls/s (statx 145 -> 58, getdents64
35 -> 10, faccessat 36 -> 1); four idle panes 1.35 % -> 0.68 % and 47.3 -> 33.7 wakeups/s;
four panes minimised 31.1 wk/s / 0.87 % -> 7.3 wk/s / 0.20 %, and back at the full rate within
the first two seconds of being restored. Per key press 417.5 statx + 170.2 faccessat -> 2.5 + 2.2,
and /etc/default/keyboard is not opened while typing at all. The "before" column reproduces the
profile's own counts to the decimal, which is what says the two are measuring the same thing.

Two notes for whoever reads the commit message:

1. Its per-key figures (statx 484 -> 70) were taken in a window that also held a one-off PATH scan
   — the shell highlighter's pathCommands() reads every directory of PATH the first time a word is
   typed in Terminal mode, ~8 600 access() calls, once for the life of the process. The clean
   figures above come from a run with a warm-up window thrown away (syscalls-per-key.txt holds
   both). The scan itself is left alone: once per process is not a hot path.
2. tunePoll() now treats "Relay is not the application in front" the way it already treats a
   background tab, which is what the card's plan asked for. A pane that is loading, has a queue or
   has a turn in flight still polls at the full rate, so only an idle pane at a prompt slows down;
   and a platform that never reports the application active (a bare X server with no window
   manager) is read as "in front", so nothing is slowed where nobody can be told.
