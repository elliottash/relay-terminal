# One pane model, two views: the phone draws the desktop's pane

## Issue

for the phone / browser app, can we make it actually run a single pane version of relay in the
browser, rather than having a separate app.

i want the phone / browser app to be as close to the PC app as possible

it will still be a remote control, so it doesnt have to be identical to the computer app. if its
faster, lets port the qt appearnace to an easier phone / tablet system first.

the phone/tablet should be able to create new conversations and observe the sessions manager.

i also want to test it on my laptop browser. and i want to test sharing sessions across relay
sessions in the actual relay terminal app on my laptop. sphinxpad should be reachable on the lan

## Decisions (owner, 2026-09-18)

- **Not** Qt for WebAssembly and **not** pixel streaming. A browser build would still need a remote
  adapter for each of the pane's 50 worker request types (several of which a client must never
  send), plus a Qt 6 port and a toolchain, and it would put a mouse-sized UI on a phone. Pixel
  streaming would let a phone's taps reach every desktop widget, which makes the capability rules
  unenforceable. So: the desktop publishes one pane model and both views draw it.
- The web view **ports the Qt appearance**: theme generated from `src/Theme.cpp`, the same layout
  order, desktop-written labels, desktop keys on a keyboard, touch sizes on a phone.
- Allowed for any device that may prompt (AGENT): **switching models** (desktop-minted choice ids,
  only presets with a stored key) and **steering**. Also **creating a conversation** and
  **observing the session manager**. Opening a past conversation remotely is **not** approved.
- Keys, provider settings, the keyring and conversation deletion stay on the desktop.
- Qt 6 port: not now.

## Live evidence

`docs/qa_evidence/2026-09-18-web-pane-view/live.sh` runs the whole path offline: a real Relay under
Xvfb against the streaming fake model, in an isolated HOME and XDG profile, shares a pane to a real
headless browser running the real client. The browser pairs, opens the pane, and the view draws the
desktop's own rows. With the desktop's message waiting for the next tool call, the phone's × on that
row withdraws it: the row goes from both screens, and the model — asked again after the tool call,
which is the step a waiting message would have ridden on — never received it.
