# One helper system: the Switchboard agent, helpers in Options/Actions/Sessions, and agents that drive the app

## Issue
One system: the Switchboard agent, the helper agents in Options, Actions and Sessions, and the pane agents' power to drive the app are one joint thing — one helper worker per tab, one chat surface, one tool set — not three features that happen to look alike (owner, 2026-09-20: "this should also include switchboard -- lets make them a single joint system").

Agents can drive the Relay app the way they already drive the Switchboard: change options, run actions, search the session manager, and open or zoom the Options, Actions, Sessions and Switchboard panes down to a row, a query or a card. When you are in Options, Actions or Sessions you have a helper agent, the same one the Switchboard has. Info and Activity get no helper of their own: they are about the pane's own agent, so that agent gets read tools over its session info and activity and an "Ask" row on those panes prefills its composer (owner, 2026-09-20).

Owner's original wording (2026-09-19): "allow agents to control the relay app, and add helper agents in the options, sessions, and actions menus. give the agents skills to change options, run actions, or search the sessions manager, like they currently have for the switchboard. it can also open those panes if you ask it, and zoom to specific items / options.. if they cant yet, also allow agents to open the switchboard and cards directly as well and zoom to them. when you are in options, actions, or sessions, you have a helper agent, same as the switchboard agent."

## Plan
**Goal.** One helper system. The Switchboard agent becomes one instance of it: a per-tab helper worker (Switchboards are per tab — owner, 2026-09-20 — and a tab holds one project) whose brief and tool scope follow the pane that asked, a chat surface any pane can embed, and a tool set — board, options, actions, sessions, navigation — that the helper and every pane agent share. Agents can change options, run safe actions, search sessions and open/zoom Options, Actions, Sessions and Switchboard (to a row, a query, a card); Options, Actions and Sessions carry the helper's panel; the pane agent can read its own session info and activity.

**Decisions (owner + agent, 2026-09-20).**
- **Single joint system, one card.** Not split into "helper agents" and "agents can control Relay": a helper in Options that can only describe an option is half a feature; "turn it on for me" needs the write side. The Switchboard is part of the same system, not its precedent.
- **One helper worker per tab, keyed by the tab, and it is the Switchboard's.** Switchboards are per tab, not per window, and the same project open in two tabs gets two Switchboards with two separate agents (owner, 2026-09-20). So the worker is keyed by the **tab**, not by the workspace: today `RelayWindow::boardWorker(workspace)` holds one `BoardWorker` per attached project and would hand both tabs the same worker and the same conversation. The map becomes tab → worker, each configured with its tab's workspace; the board's *files* stay one set shared by every tab on the project (that is what #TTYB already arranged for the panes' data), only the conversation and the queue are the tab's own. The conversation is persisted per (project, tab) under the tab's persistent id — the one that restores its panes — so a restart brings each tab's helper back with its own history. Two tabs on one project cost two workers and two warm-ups; that is the owner's choice. That worker is generalised rather than joined by a sibling; the Options, Actions and Sessions panes in a tab ask the tab's worker, so one conversation spans the tab's board and its panes. A tab with no project attached gets a worker with no board (app tools only), started on the first ask rather than when the tab opens. `BoardWorker` (`src/BoardWorker.{h,cpp}`, `agent_role: "switchboard"`) is that worker; the `switchboard` role in `backend/relay_core/roles.py` stays the helper's role (its model box #BRD3, its Options › Models row and its Main default already exist), so no settings migration. Each ask carries a `pane` hint that picks the brief. Whether the role's label becomes "Helper agent" once it serves more than the board is the owner's call.
- **One chat surface.** `BoardChatPanel` (`src/BoardChat.{h,cpp}`: composer on its own row, model box / microphone / Send on a strip under it, 79af8640) is lifted into the shared panel; the Switchboard keeps a subclass for the survey, the queue and Check/Clean up. Options, Actions and Sessions embed the panel collapsed — one "Ask about this pane" row that expands — because the Switchboard's 320 px of log plus composer is most of a small pane.
- **One tool set.** `board_*` (existing) plus the new `app_*` tools, attached to the helper worker and to every pane agent alike; what differs per agent is the brief and the settable/`agent_safe` markers, not the tools.
- **Info and Activity: deferred as helpers, covered by the pane agent.** Those panes are about the pane's own agent and their data is that worker's own turn events and state, so a second agent reading a ledger about the first is the roundabout way to answer "why was that turn slow". Two read tools on the pane agent instead — `session_info` and an `activity` digest, **windowed** (last N turns, one turn by id, slowest tool calls), never the whole ledger, so answering "why is my context low" does not lower it — and an "Ask" row on both panes that prefills the pane's composer and focuses it (the Check-finding draft pattern). The few GUI-only Info fields (pane id, tab, share state) ride on `configure` or the tool says it cannot see them.

**Findings.**
- The Switchboard agent is the model to copy: a per-window lightweight worker (`src/BoardWorker.{h,cpp}`, started with `agent_role: "switchboard"`, RelayWindow.h:4604 `startBoardWorker`), backend tool set in `backend/relay_core/board_tools.py` (`BoardTools`), attached to the agent as `agent.board` and merged into the tool list in `backend/relay_core/agent.py` (`Agent.tools()`, :637-645; dispatch :2194-2228). Pane-embedded chat UI lives in `src/BoardChat.{h,cpp}` (protocol 19.18), with the card thread reply box in `src/BoardPane.{h,cpp}`.
- Options and Actions are one widget, `src/SettingsPane.{h,cpp}` (`Mode::Options`/`Mode::Actions`), fed by two GUI-side catalogs RelayWindow builds: `settingsSections()` (`SettingRow` with stable `id`, reader/writer closures, kinds Toggle/Choice/Text/Number/Button…) and `searchableActions()` (`ActionItem` with `key`, `run`). Navigation entry points already exist: `openSettingsPane(mode, tab, search)`, `SettingsPane::revealOption(sectionId, rowId)` (the "zoom to an option" primitive), `openSessions(tab, query)`, `openBoardCard(id)` (RelayWindow.h:1255, 3740, 4427).
- The Sessions pane (`src/Conversations.{h,cpp}`, `SessionManager`) never talks to the worker itself; search is worker-side via the protocol-14 `conversations` message (`backend/relay_core/session_protocol.py`, `SessionIndex.search`), so a backend tool can search sessions without the GUI.
- Precedent for shipping a GUI catalog to the worker: the `keybindings` catalog — sent in `configure`, refreshed by a `keybindings` message (`backend/worker.py`:148, 239-246). Options/actions catalogs can ride the same pattern.
- There is **no** worker→GUI navigation/command channel today; Pane handles a fixed set of event types (Pane.h:8891-9352). A new event type is needed, forwarded Pane → RelayWindow the way `onOpenCard` is (Pane.h:648, RelayWindow.h:4944).
- Everything the Activity pane draws arrives as the worker's own turn events (reasoning, tool calls, usage), and Info's figures (model, tokens, context left, sandbox) are worker state, so the pane agent's read tools need no new data collection — only a digest over what the worker already holds.

**Steps** (each a narrow area; one subagent per step, landing its own files through `scripts/land.py`).
1. **Protocol (docs/AGENT-SESSIONS-PROTOCOL.md).** New section "The agent drives the app": the `app` block on `configure` (options catalog: section/row ids, labels, kinds, current values, `settable` flag; actions catalog: key, section, label, `agent_safe` flag), an `app_catalog` refresh message (mirrors `keybindings`), the `app_command {command, …}` worker→GUI event and its `app_command_result {id, ok, error}` GUI→worker answer, `helper_ask {id, pane, text}` GUI→worker with the answer streaming as `chat: true` turn events tagged with the pane, and 19.18 restated as the helper's panel with the Switchboard as one pane of it. Update docs/ARCHITECTURE.md and docs/SWITCHBOARD-DESIGN.md §4.
2. **Backend `backend/relay_core/app_tools.py` — `AppTools`, mirroring `BoardTools`.** Tools: `app_option_list`/`app_option_get {section?, row?}`; `app_option_set {section, row, value}` (validated against the catalog; secrets rows — API keys — are never settable); `app_action_list {search?}`, `app_action_run {key}` (only `agent_safe` actions); `app_sessions_search {query, scope?, limit?}` answered worker-side through the session index; `app_open {target: options|actions|sessions|switchboard, section?, row?, query?, card?}` emitting `app_command {command: "open"}`. Writes/action runs emit `app_command` with a request id and block on `app_command_result` (the `BoardInit.ask` round-trip pattern), so the tool result says what actually happened. Attach as `agent.app` in `agent.py` exactly like `agent.board`, with a short system-prompt section and a per-pane brief table (`pane` → paragraph).
3. **Pane agent read tools (backend).** `session_info` and `activity {turns?, turn?, slowest?}` over the worker's own transcript, usage and tool-call timings — windowed digests, with tests that a whole-session ask returns a bounded result.
4. **Worker wiring (`backend/worker.py`).** Parse the `app` block of `configure` and the `app_catalog` refresh into a catalog object (like `KeybindingCatalog.from_request`); build `AppTools` and hand it to the `Agent`; route `app_command_result` to the pending tool call; route `helper_ask` by pane.
5. **GUI command handling (`src/RelayWindow.h`, `src/Pane.h`).** RelayWindow builds the app catalog from `settingsSections()` + `searchableActions()` and sends it with every pane `configure` (and on `SettingsWatch` change). Pane gains `onAppCommand`; RelayWindow executes: `open` → `openSettingsPane` / `revealOption(section, row)` / `openSessions(tab, query)` / `openBoardCard(card)`; `set_option` → find the row and invoke its writer; `run_action` → find the `ActionItem` and `run()` it. Every outcome answers `app_command_result`. ActionItems and SettingRows gain an `agentSafe`/settable marker; destructive actions (delete session, reset to defaults) and secret rows default to off.
6. **The helper worker (`src/BoardWorker.{h,cpp}`, `src/RelayWindow.h`, `backend/relay_core/board_chat.py`).** Re-key `m_boardWorkers` from workspace to tab (`boardWorker(tab)`), each instance configured with its tab's workspace, so two tabs on one project run two workers with two conversations over one set of board files; persist the conversation per (project, tab) under the tab's persistent id. Generalise the worker so it serves the Switchboard and the three panes: it is configured with the app catalog as well as the board, an ask from any pane in the tab reaches it with its `pane` hint, and a tab without a project gets a board-less instance on its first ask. Closing a tab stops its worker; the board's `chat` block and queue events carry the tab so one tab's answer never redraws another's panel.
7. **The surface (`src/BoardChat.{h,cpp}` → shared panel; `src/SettingsPane.{h,cpp}`; `src/Conversations.{h,cpp}`).** Lift `BoardChatPanel` into a panel that takes a `pane` name; the Switchboard keeps its subclass (survey, queue, Check/Clean up). Options/Actions (one panel, both modes) and Sessions embed it collapsed behind an "Ask about this pane" row. Answers' links resolve into the pane (an option id reveals the row, a session id opens it, a card id opens the card).
8. **Info and Activity "Ask" rows (`src/SessionInfo.{h,cpp}`, `src/AgentInternalsView.{h,cpp}`).** One row each that prefills the owning pane's composer with a question about what is on screen and focuses it. No agent in these panes.
9. **Shortcut hints and docs (WARP.md standing rule).** Hints for the ask key in every pane that gets one; the role label question for the owner.

**Decided by the owner, 2026-09-20 ("yes to all, go").**
1. **Settable options:** every value row — Toggle, Choice, Number, Text — except secrets (API keys, anything the keyring holds), which no agent may set. Button rows are not values; they are actions (item 2). The catalog carries `settable` so a row can be excluded later with one line.
2. **`agent_safe` actions:** opt-in per action, starting with the reversible ones — open/reveal anything, test a key, refresh/detect local servers, copy this page, reorder models, undo. Off until the owner says otherwise: reset to defaults, remove a key or a server, delete a session, pairing/sharing, quit/restart. The line is "undoable in one click".
3. **Main pane agent gets the write tools on by default**, behind one toggle in Options › Agent ("Agents may change options and run actions") that gates the helper and the pane agent together.
4. **The `switchboard` role is relabelled "Helper agent"** — label only; the internal name, settings, protocol and model box are untouched. Each panel's header says where it is ("Switchboard agent", "Options helper", "Sessions helper").
5. **The per-tab helper starts on the first ask**, not when the tab opens.
6. **Every change an agent makes is visible and undoable in one step** (owner: "it should be clear what's changed / done and reversion / undo should be easy"). A write emits an `app_change` the GUI shows as "Agent changed <label>: <before> → <after> · Undo" (a notification with an Undo action, and the tool result in the transcript says the same); the GUI keeps the change log and performs the undo itself, so Undo works with no agent involved; `app_changes` / `app_undo` let the agent list and revert its own changes; an option row changed by an agent carries a marker until the person touches it.
