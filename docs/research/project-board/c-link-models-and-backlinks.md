# Pass C: Link models and backlinks in plaintext knowledge systems and project trackers

*Research for Relay's project Board (cards, skills, memories, artifacts/runs, cases, live panes, with links among them). Researched 2026-09-25 against primary documentation; every claim cites a URL that was read. Anything not confirmed from a primary source is marked *unverified*.*

The Board's link question has four parts: **what a link points at** (a title, a path, a stable id, or a non-file target such as a commit), **whether the relation has a type** (blocks / duplicates / related) and whether users fill it, **where the reverse direction lives** (stored on both ends, or recomputed from the forward links at read time), and **what happens under rename and under a git merge made by several agents at once**. Each system below is read for those four questions.

## 1. Obsidian

**Link forms.** Obsidian's internal link is the wikilink `[[Three laws of motion]]`, with a heading form `[[About Obsidian#Links are first-class citizens]]`, a block form `[[2023-01-01#^37066d]]` (auto-generated 6-hex block id, or a human-readable `^quote-of-the-day` limited to Latin letters, numbers and dashes) and a display alias `[[Example|Custom name]]`; the Markdown form `[Three laws of motion](Three%20laws%20of%20motion.md)` is equivalent, and "by default, due to its more compact format, Obsidian generates links using the Wikilink format" ([Internal links](https://obsidian.md/help/links)). The target is a **title/path, not an id**: a note is addressed by its file name, and the block id is the only stable-id construct in the format.

**Rename.** Links are kept working by rewriting: "Obsidian can automatically update internal links in your vault when you rename a file" (Settings → Files and links → Automatically update internal links) ([Internal links](https://obsidian.md/help/links)). That is a *write-time* fix that only runs when the app is the thing doing the rename; a `git mv` or a rename in another editor leaves every wikilink dangling, and the format has no way to tell a dangling link from a deliberate link to a note that does not exist yet ("a note doesn't need to exist to link to it", [Graph view](https://obsidian.md/help/plugins/graph)).

**Backlinks are computed, never stored.** "A backlink for a note is a link from another note to that note." The Backlinks pane splits them into **linked mentions** ("backlinks to the notes that contain an internal link to the active note") and **unlinked mentions** ("backlinks to any unlinked occurrence of the name of the active note") ([Backlinks](https://obsidian.md/help/plugins/backlinks)). Nothing is written to the linked-to file; the index is the app's in-memory metadata cache, rebuilt from the files. Unlinked mentions are the useful half of this for a Board: a plain-text scan for the *name* of an object (`#K7Q2`) finds references that nobody bothered to make into a link.

**Typed links via properties.** Front-matter properties can hold links: "Internal links in text properties must be surrounded with quotes" and the same for list properties ([Properties](https://obsidian.md/help/properties)). The property *key* is the type (`related: ["[[A]]", "[[B]]"]`), so typing is free-form and per-vault; the six property types are text, list, number, checkbox, date, date & time, with no "link" or "relation" type ([Properties](https://obsidian.md/help/properties)). Whether property links are rewritten on rename is not stated on the help pages read; a third-party plugin README claims Markdown-style links in properties "do not resolve … and do not register as a backlink" while wikilinks in properties do ([Frontmatter Markdown Links listing](https://www.obsidianstats.com/plugins/frontmatter-markdown-links)) — *unverified* against Obsidian's own docs.

**Dataview** exposes the computed reverse direction as an implicit field: `file.inlinks` — "a list of all incoming links to this file, meaning all files that contain a link to this file" — beside `file.outlinks`, `file.path`, `file.name` ([Dataview metadata](https://blacksmithgu.github.io/obsidian-dataview/annotation/metadata-pages/)). This is the cleanest published statement of the pattern Relay wants: **store only forward links in the files; the reverse is a query over the index.**

**Bases (2025).** "Bases is a core plugin that lets you create database-like views of your notes", "saved as a `.base` file", with Table, List, Cards, Kanban and Map views over files and their properties ([Bases](https://obsidian.md/help/bases)). It is a saved query over property values; the help page read does not document a backlinks field, so treat Bases as a view over the *forward* links held in properties.

**Graph view.** "Circles represent notes, or nodes", "lines represent internal links between two nodes", and a node grows with the number of nodes referencing it; there is a local graph with a depth slider, and the "Existing files only" filter exists precisely because dangling links clutter the picture ([Graph view](https://obsidian.md/help/plugins/graph)). Users on the Obsidian forum say the same: "I only use the local graph view, because the full graph has become completely useless as the number of notes has grown and there is no way to add types on notes or name and properties on relationship or select what should be displayed or not"; the global graph is "very beautiful to look at, impressive for people you show it to, but for me not exploitable in any useful way" ([forum: How do you use the graph view?](https://forum.obsidian.md/t/how-do-you-use-the-graph-view/2785)). The local graph at depth 1 is the only part that is a working tool (it is the backlinks pane drawn as a picture); the vault-wide graph is a demo. A Board should ship the local, depth-1 neighbourhood of a card and skip the hairball.

## 2. GitHub cross-references, sub-issues, dependencies, permalinks

**Reference forms.** Autolinks recognise `#26`, `GH-26`, `jlord/sheetsee.js#26` and the full URL for issues, PRs and discussions; commits by `a5c3785ed8d6a35868bc169f07e40e889087fd2e`, `jlord@a5c3785…` and `jlord/sheetsee.js@a5c3785…` ([Autolinked references](https://docs.github.com/en/get-started/writing-on-github/working-with-advanced-formatting/autolinked-references-and-urls)). Three lessons: the short form is *scoped* (`#26` means "this repo"), the qualified form is a **path prefix on the same token** (`owner/repo#26`, `owner/repo@sha`) rather than a different syntax, and a commit is a first-class link target with its own sigil (`@`).

**Reverse direction is an event, not a field.** The docs say "manually linking to an issue in a pull request will automatically generate another link from the issue *back* to the pull request" ([Autolinked references](https://docs.github.com/en/get-started/writing-on-github/working-with-advanced-formatting/autolinked-references-and-urls)), and the REST timeline exposes that as a **cross-referenced event** carrying `actor`, `created_at`, `updated_at` and `source: {type, issue}` ([Timeline events](https://docs.github.com/en/rest/issues/timeline)). So GitHub does not store a backlink on the target; it appends an *append-only, timestamped* record of "X mentioned you" to the target's timeline, computed when the source is saved. That is a stored backlink, but one that never needs merging because it is a log entry rather than a field.

**Typed closing links.** `close/closes/closed/fix/fixes/fixed/resolve/resolves/resolved #10` or `Fixes octo-org/octo-repo#100`, one keyword per issue ("Resolves #10, resolves #123, resolves octo-org/octo-repo#100"); "when you merge a linked pull request into the default branch of a repository, its linked issue is automatically closed" ([Linking a PR to an issue](https://docs.github.com/en/issues/tracking-your-work-with-issues/using-issues/linking-a-pull-request-to-an-issue)). The type lives in the *prose* (a keyword before the reference), which is the one typed-link convention that people demonstrably fill in, because it does something (closes the issue) and it costs one word.

**Sub-issues (GA 2025).** "You can add sub-issues to an issue to break down larger pieces of work into tasks", "up to 100 sub-issues per parent issue", "up to eight levels of nested sub-issues", and cross-repo parents are allowed ([Adding sub-issues](https://docs.github.com/en/issues/tracking-your-work-with-issues/using-issues/adding-sub-issues)). Parent-child is a structural relation stored by the platform, not a reference in text.

**Issue dependencies (2025–26).** "Issue dependencies let you define issues that are blocked by, or blocking, other work", added from a "Relationships" sidebar with "Mark as blocked by" / "Mark as blocking", or `gh issue edit --add-blocked-by / --add-blocking`; "blocked issues are marked with a 'Blocked' icon on your project boards" ([Creating issue dependencies](https://docs.github.com/en/issues/tracking-your-work-with-issues/using-issues/creating-issue-dependencies)). After fifteen years with only free-text references, GitHub's *entire* typed vocabulary is: parent/sub-issue, blocked-by/blocking, closes, duplicate (via the "Duplicate of" close reason) — the same four that appear everywhere below.

**Permalinks.** "Instead of using a branch name in the URL … put a commit ID. This will permanently link to the exact version of the file in that commit", because "the version of a file at the head of branch can change as new commits are made"; `y` rewrites the current URL to the permalink ([Permanent links](https://docs.github.com/en/repositories/working-with-files/using-files/getting-permanent-links-to-files)). Path plus commit is the stable address for a line of code; path alone is not.

## 3. Linear issue relations

**Relation types.** Linear's issue relations are **blocked, blocking, related, duplicate** — four, no more; blocked/blocking are the two directions of one relation ("Mark issues as blocked by other issues", "Mark issues as blocking other issues"), created with `M` then `B` / `M` then `X`, `M`+`R` for related ([Issue relations](https://linear.app/docs/issue-relations)). The same page states the auto-linking rule that GitHub also has: "When you reference issues in a description or comment, they'll automatically become a related issue" — a mention in prose *is* an untyped `related` link, computed from the text, without anyone choosing a type.

**Duplicate is a state, not just a link.** Marking a duplicate "marks the issue you are viewing or have selected as a duplicate and moves it into the reserved Duplicate status", with "a dedicated banner and sidebar treatment that links back to the original issue" ([Issue relations](https://linear.app/docs/issue-relations)). Duplicate is the one relation type that changes the source's lifecycle, which is why it survives as a distinct type rather than folding into `related`.

**Parent/sub-issue is structural.** It is a separate mechanism from relations: "when the parent issue is marked as done, all remaining sub-issues will also be marked as done" if the team enables the automation, and "when you convert a parent issue into a project, the original issue and its sub-issues are added to the project as standalone issues" ([Parent and sub-issues](https://linear.app/docs/parent-and-sub-issues)). The single-parent rule is not stated on the page read (*unverified*).

**Containment is a field, not a link.** "An issue belongs to a team and moves through that team's workflow"; "projects group issues together around a shared outcome"; "an initiative can contain multiple projects" ([Conceptual model](https://linear.app/docs/conceptual-model)). Issue→project and project→initiative are single-valued attributes of the child; the reverse (a project's issue list) is a query. **Documents** attach the other way: "Add documents to projects, initiatives, teams, issues, or cycles", and "reference documents in issue descriptions, comments, agent guidance fields" by @-mention ([Documents](https://linear.app/docs/documents)) — one attachment link and one mention link, nothing typed.

**Commits and PRs.** The identifier `TEAM-123` in a branch name or PR title/body links the PR; the closing magic words are "close, closes, closed, closing, fix, fixes, fixed, fixing, resolve, resolves, resolved, resolving, complete, completes, completed, completing, implement, implements, implemented, implementing, linear issue", used as "Fixes ENG-123"; on the issue "a banner will appear at the top" and "Linear posts a linkback message as a comment" ([GitHub integration](https://linear.app/docs/github)). Same shape as GitHub: a typed link is a keyword before an id in text, and its reverse is a *comment/event* on the target.

## 4. Notion relations and rollups

**One-way by default, two-way on request.** A relation property is one-way unless "Show on [database name]" is toggled, which "creates corresponding relation properties in both databases where edits sync bidirectionally": "with two-way relations, the edits work both ways! So if you add a customer to the Items database in the relation column, the change pops up in your Customers database" ([Relations and rollups](https://www.notion.com/help/relations-and-rollups)). Notion can afford a *stored* two-way link because one server owns both ends and writes them in one transaction; a file-per-object system in git has no such transaction, which is the whole argument against copying this model.

**Self-relations show the asymmetry problem.** For a database related to itself with two-way off, "the relation can work in both directions. If you add Task B to Task A, Task A can also show up on Task B"; turning two-way on creates *named directional pairs* such as "Next task" / "Previous task" that "update automatically when you add pages to one" ([Relations and rollups](https://www.notion.com/help/relations-and-rollups)). That is Jira's outward/inward naming rediscovered: a directed relation needs two names, one per end.

**Rollups.** "Rollups help you aggregate data in your databases based on relations" (Sum, Average, Count, date ranges); a rollup of a rollup is refused "as this could create unintended loops" ([Relations and rollups](https://www.notion.com/help/relations-and-rollups)). Cardinality is a per-property switch: "1 page" or "No limit". No per-database cap on the number of relation properties is documented on this page (*unverified*).

## 5. org-mode and org-roam

**Link locators.** Org links are "URL-like locators" — a type, a colon, no space — with `file:sometextfile::NNN` (line), `file:projects.org::some words` (text search), `id:B7423F4D-2E8A-471B-8810-C40F074717E9::*task` (a UUID node plus an in-node headline search), and http, mailto, elisp, shell, docview, doi, info among the built-in types ([External links](https://orgmode.org/manual/External-Links.html)). The `::` search suffix is the org answer to "link to a line at a commit" — a *secondary* locator inside the primary target, which degrades to a text search when the line moves.

**Ids on demand.** `org-store-link` stores "a link to the current location"; for a headline it uses `CUSTOM_ID` if present, and "in addition or alternatively … create and/or use a globally unique 'ID' property", which "can be either a UUID (default) or a timestamp, depending on `org-id-method`" ([Handling links](https://orgmode.org/manual/Handling-Links.html)). Org's rule is: a heading gets an id **the first time something links to it**, not before, so most headings never carry one. Resolving an `id:` link across files depends on the `org-id-locations` cache file (a per-machine id→file map), which the manual pages read here do not describe (*unverified* on this run; well known in practice) — it is the weak point across machines because the map has to be rebuilt when files move.

**org-roam: the computed backlink db.** "A node is any headline or top level file with an ID"; "we link between nodes using Org's standard ID link (e.g. `id:foo`). While only ID links will be considered during the computation of links between nodes, Org-roam caches all other links in the documents for external use"; "Org-roam uses a SQLite database to perform caching", kept current by `org-roam-db-autosync-mode` ("run functions on file changes to maintain cache consistency"), and "cache builds may take a while the first time, but subsequent builds are often instantaneous because they only reprocess modified files"; the buffer shows "Backlinks: view (preview of) nodes that link to this node. Reference Links: nodes that reference this node" ([org-roam manual](https://www.orgroam.com/manual.html)). The manual's own framing is the design principle: "Org-roam simply builds an auxiliary database to give the personal wiki superpowers … The notes are still functional even if Org-roam ceases to exist." Files hold forward `id:` links only; the db is a derived, per-machine, incremental cache; `ROAM_REFS` lets a node claim an external identifier (a URL, a citekey) so that references to it become "reference backlinks", and `ROAM_ALIASES` gives a node extra names without renaming. That is exactly the three-part shape Relay's Board already has: stable id in the object, forward links in files, an index rebuilt from files.

## 6. Beads (`bd`)

**Typed, directed, and split into two classes.** Beads' dependency doc divides types by whether they affect readiness. Blocking (they change `bd ready`): `blocks` (default, "B cannot start until A closes"), `parent-child` ("children blocked when parent blocked"), `conditional-blocks` ("B runs only if A fails"), `waits-for` ("B waits for all of A's children"). Non-blocking, "graph annotations only": `related` ("informational link"), `tracks`, `discovered-from` ("found during work on another issue"), `caused-by` ("root cause link"), `validates` ("test or verification link"), `supersedes` ("replaced by a different issue") ([Dependencies and gates](https://github.com/gastownhall/beads/blob/main/docs/core-concepts/dependencies.md)). The direction convention is `bd dep add issue-2 issue-1` = "issue-2 depends on issue-1": first argument is the dependent, second the dependency ([same](https://github.com/gastownhall/beads/blob/main/docs/core-concepts/dependencies.md)). The README's short list is still "blocks, related, parent-child" plus "`relates-to`, `duplicates`, `supersedes`, and `replies-to` for knowledge graphs" ([README](https://raw.githubusercontent.com/gastownhall/beads/main/README.md)) — the vocabulary has grown to ten types in a year, and the doc has to explain which ones matter. The lesson is the split, not the list: **one blocking relation that the scheduler reads, and everything else is an annotation**.

**`discovered-from` is the agent-era addition.** It records provenance ("found during work on another issue") — for Relay this is the link from a card filed mid-session to the card whose work surfaced it, which is what a `cases.jsonl` row and a card thread already imply but do not name.

**Ids and storage.** "Hash-based IDs (`bd-a1b2`) prevent merge collisions in multi-agent/multi-branch workflows", with hierarchical children `bd-a3f8.1`, `bd-a3f8.1.1` ([README](https://raw.githubusercontent.com/gastownhall/beads/main/README.md)). Storage has moved off files: "`.beads/issues.jsonl` is an export for viewers and interchange, not the source of truth or a backup"; Dolt is authoritative; "JSONL import is upsert-only; it cannot infer that records absent from an export were deleted, pruned, or simply never exported", and post-merge hooks "skip JSONL import when `sync.remote` is configured" ([Sync concepts](https://raw.githubusercontent.com/gastownhall/beads/main/docs/core-concepts/sync-concepts.md)). The dependencies doc still notes the file-backed mode's virtue: "with file-based storage (JSONL), issue updates land atomically with code in the same commit" ([Dependencies](https://github.com/gastownhall/beads/blob/main/docs/core-concepts/dependencies.md)). Read this as a warning about the *reverse* direction: a JSONL row per dependency edge merges cleanly (append-only lines, hash ids), but a deletion cannot be expressed as "the line is missing" — which is exactly the failure a stored backlink field would have in git.

**The edge record.** An exported dependency is one row per edge, `{"issue_id":"x-bie","depends_on_id":"x-aeb","type":"discovered-from","created_at":…,"created_by":…}` in `bd list --json` / `bd export`, while `bd show --json` inlines the target issue with a `dependency_type` field instead — and the two shapes have already bitten tooling ("silent nulls") ([beads #5592](https://github.com/gastownhall/beads/issues/5592)). Two conclusions for Relay: **store the edge once, on the source, as `(target, type, when, by)`**, and never publish two shapes for the same edge.

## 7. Jira and Confluence

**Named, directional, admin-definable.** A Jira link type has three strings: "the title for the link type", "the description of how a work item affects other work items" (outward) and "the description of how a work item is affected by other work items" (inward); admins "edit the Name, Outward description, and Inward description" or "add a new link" ([Configure issue linking](https://support.atlassian.com/jira-cloud-administration/docs/configure-issue-linking/)). Defaults visible to users: blocks / is blocked by, clones / is cloned by, duplicates / is duplicated by, relates to, and further types (merged into/from, reviews/is reviewed by, causes/is caused by, implements/is implemented by, added to idea/is idea for) that "can be configured by Jira admins. If an admin deletes a link type, it won't be available to use" ([Link work items](https://support.atlassian.com/jira-software-cloud/docs/link-issues/)). The relation is stored **once** as a directed edge and each end is rendered with its own description — Jira never stores the inverse. That is the correct model for a file-per-object store too: one edge, two display names. Parent/child (epic → story, subtask) is a separate structural field, not a link type. **Confluence ↔ Jira is a stored reciprocal link, and it drifts.** A Jira issue macro on a Confluence page is supposed to create a "Mentioned in" link on the issue; Atlassian's own knowledge base documents the case where "the Confluence page is not showing up in the 'Mentioned in' link within the Jira issue", says "the root cause is unknown at this time", and offers as workarounds cloning the page or removing and re-adding the issue key to force Confluence to resend the linking request ([KB: 'Mentioned in' not displaying](https://support.atlassian.com/jira/kb/mentioned-in-confluence-page-is-not-displaying-on-individual-jira-issues/)). Two systems each storing one end of a link, joined by a request, is the textbook stale-two-way-link failure.

## 8. Logseq

**Page refs are names, block refs are ids.** `[[page]]` creates or references a page and `#tag` is the same reference in tag clothing; a block reference is "clickable link to a particular Logseq block e.g. `((123e4567-e89b-12d3-a456-426614174000))`", made by "putting a unique UUID inside parenthesis `(())`" and chosen from an autocomplete search ([Block Reference](https://raw.githubusercontent.com/logseq/docs/master/pages/Block%20Reference.md), [Page and block references](https://raw.githubusercontent.com/logseq/docs/master/pages/Page%20and%20block%20references.md)). In file graphs the referenced block gains an `id:: <uuid>` property line in its source file — the app *writes into the target* to give it a stable address (well known from the file format; the docs page read does not state it, so *unverified* here). Linked and unlinked references at the bottom of a page are computed from the DataScript db, like Obsidian.

**The documented failure.** logseq/logseq #7362, "Block references are lost from the DB if the file containing the referenced block is reloaded from disk": "when a file is re-loaded into the DB due to a change on the file system (e.g. manually saving that file on disk, a dropbox sync from another computer, etc.), any references to blocks on that page via UUID are *deleted* from the db, even if the block remains", because the reload deletes and re-adds the blocks and "references from other pages to that UUID will not be restored" ([issue #7362](https://github.com/logseq/logseq/issues/7362)). The forward links in the files were fine; the *index* lost them because it treated a file reload as a delete. Any Board index that ingests files git is rewriting underneath it needs to be rebuilt from the files, not patched by events. A feature request to "drop UUID for blocks in favor of short codes" ([discuss.logseq.com](https://discuss.logseq.com/t/drop-uuid-for-blocks-in-favor-of-short-codes/21219)) records the human cost of 36-character ids in prose — which is what Relay's 4-character ids are for.

## 9. Dendron and Foam

**Dendron: id in front matter, name in the link.** Every note carries front matter `id` ("a globally unique identifier for the note", "lowercase, alphanumeric, and 23 characters long" by default), `title`, `created`, `updated`; users may "change all existing variables except the id field" because "features like publishing depend on it to find the right link" ([Frontmatter](https://wiki.dendron.so/notes/ffec2853-c0e0-4165-a368-339db12c8e4b/)). Yet wikilinks address the hierarchical *name*, `[[recipes.italian.desserts.tiramisu]]`, `[[label|your.note.to.link]]`, `[[recipes.italian.desserts.gelato#best-ingredients]]` ([Linking notes](https://wiki.dendron.so/notes/9MZBqhrijEM4QpZRa5t08/)), so rename is a rewrite: "Dendron: Rename Note … will also update all references in other notes of that note" ([Rename Note](https://wiki.dendron.so/notes/g0iqmyiyxje6ndjmecshb8b/)). Dendron thus has the stable id *and* links by name anyway, because names are what humans type; the id is for URLs and the index. That split — id for machines and published URLs, readable name in prose, rewrite on rename — is a reasonable position only when one tool owns every rename.

**Foam: computed backlinks, optional materialised links.** "Backlinks are discovered automatically by Foam" from `[[wikilinks]]`; the Connections panel shows "both forward links and backlinks" ([Backlinking](http://docs.foam.md/features/backlinking)). Wikilinks are "identifier links — `[[filename]]`, `[[folder/filename]]` — identify a resource by name, resolved relative to the whole workspace"; with duplicates "Foam resolves it alphabetically (deterministic), and shows a warning diagnostic"; "when you rename or move a note or folder, Foam automatically updates all wikilinks pointing to it" (`foam.links.sync.enable`) ([Wikilinks](http://docs.foam.md/features/wikilinks)). Its **link reference definitions** are the one plaintext system that *materialises* resolved links into the file: `[Data Science]: data-science.md 'Data Science'` appended at the bottom so GitHub renders the wikilink, with `"foam.edit.linkReferenceDefinitions": "off"` recommended "if you are using your notes only within Foam … (also to reduce clutter)" ([Link reference definitions](http://docs.foam.md/features/link-reference-definitions)). It is a generated footer, clearly bounded, regenerated on every save — the only tolerable form of "stored resolved link" in a git file, and even so it is off by default for clutter and merge noise.

## 10. Zettelkasten practice

The canonical argument for ids over titles: "You could also use the title of the Zettel as its ID. As long as it is unique, it can serve as an ID. Consequently, you cannot change the title unless you change any reference to it if you want to keep your links intact", whereas "a time-stamp is a very simple way to create a unique string of numbers to which you can refer" ([Introduction to the Zettelkasten method](https://zettelkasten.de/introduction/)). And the argument for context on a link, which is the practitioner's form of "typed links": "If you just add links without any explanation you will not create knowledge. Your future self has no idea why he should follow the link" ([same](https://zettelkasten.de/introduction/)). Relay's four-character content-stable ids are the Zettelkasten position; the sentence around `#K7Q2` in a card is the link's type.

## 11. Tana and Anytype

**Tana.** "Supertags turn a node into a typed object with a template of fields"; fields are "attributes that describe the object that the supertag represents", and a field can hold node references, with search nodes that "customize its results based on the supertag instance" — e.g. a Project supertag whose field lists its Tasks ([Supertags](https://outliner.tana.inc/learn/features/supertags)). Typed links here are *fields on a type*, which is Notion's relation property with the schema attached to the tag instead of the database.

**Anytype.** Objects have Properties that "help you describe your Objects and link them together — such as connecting a book to its movie adaptation, or a meeting to a specific project", and the reverse direction is automatic: "You can use the Backlinks property in the Object Header to check which Objects link to the currently opened one" ([Anytype docs](https://doc.anytype.io/anytype/llms-full.txt)). Typed forward property, computed untyped backlinks — the same pairing as Obsidian properties + Dataview `file.inlinks`.

## 12. Trello

"Link cards are a card type in Trello. They are automatically created when a URL is added to a new card's title", and they "aren't designed to hold extra details like comments, due dates, descriptions" ([Link cards](https://support.atlassian.com/trello/docs/link-cards/)). Card mirroring goes further: "it lets you view and edit a card from multiple locations, and ensures that changes are reflected on all mirrored versions of the original card" — when you open a mirror "you're viewing and editing the source card"; on a free workspace "it will instead create a Link card" ([Card mirroring](https://support.atlassian.com/trello/docs/mirroring-cards/)). A mirror is not a copy but a second *view* of one record, which is the only way two-way sync stays consistent: one owner, no second store. Card-to-card attachments (the Trello attachment type) are untyped, one-directional, and do not sync fields. Trello never grew a typed relation vocabulary at all.

## Cross-cutting findings

The four practice questions from the brief, answered from the sections above.

**Read-time backlink index vs stored bidirectional links.**
- Files store forward links only, everywhere a file is the record: Obsidian ([Backlinks](https://obsidian.md/help/plugins/backlinks)), org-roam ("auxiliary database … the notes are still functional even if Org-roam ceases to exist", [manual](https://www.orgroam.com/manual.html)), Logseq, Dendron, Foam ([Backlinking](http://docs.foam.md/features/backlinking)).
- Stored two-way links exist only where one process writes both ends atomically: Notion's "Show on" pairs ([Relations](https://www.notion.com/help/relations-and-rollups)), Linear, Jira's single edge with two names ([Configure issue linking](https://support.atlassian.com/jira-cloud-administration/docs/configure-issue-linking/)).
- The stored reciprocal that crosses a boundary drifts: Confluence → Jira "Mentioned in" ([KB](https://support.atlassian.com/jira/kb/mentioned-in-confluence-page-is-not-displaying-on-individual-jira-issues/)).
- GitHub's middle path, an append-only cross-reference event on the target's timeline ([Timeline events](https://docs.github.com/en/rest/issues/timeline)), is the only stored-reverse form that merges trivially, because it is a log line and never edited.
- What drifts in git is any *edited* reverse field; what merges is a forward list on the source plus appended lines elsewhere.

**Typed vs untyped links.**
- Untyped is the default that gets used: mentions in prose become `related` automatically in Linear ([Issue relations](https://linear.app/docs/issue-relations)) and unlinked mentions are surfaced in Obsidian and Logseq.
- The typed set that survives across GitHub, Linear, Jira defaults and Beads' blocking class is blocks, parent, duplicate, related; each of those triggers behaviour (readiness, roll-up, close).
- Typing is cheapest as a keyword in text (`Fixes #10`, `Fixes ENG-123`) or as a field name (`blocked_by:`), never as a picker with a dozen entries.

**Link targets that are not files.**
- Commits: `owner/repo@sha` on GitHub; permalinks are path + sha ([Permanent links](https://docs.github.com/en/repositories/working-with-files/using-files/getting-permanent-links-to-files)).
- URLs and external ids: org-roam `ROAM_REFS` lets a node *claim* an external identifier so references to it count as backlinks ([manual](https://www.orgroam.com/manual.html)); Trello turns a pasted URL into a Link card ([Link cards](https://support.atlassian.com/trello/docs/link-cards/)).
- Run/case ids: Beads' `discovered-from` edge and `created_by` on the edge record are the closest precedent ([#5592](https://github.com/gastownhall/beads/issues/5592)).

**Id stability across rename and machines.**
- Assign ids to the object, not the file: Dendron's front-matter `id` ([Frontmatter](https://wiki.dendron.so/notes/ffec2853-c0e0-4165-a368-339db12c8e4b/)), org `:ID:`, Logseq block `id::`, Beads hash ids ([README](https://raw.githubusercontent.com/gastownhall/beads/main/README.md)).
- Sequential ids collide across machines; hash or content-stable ids do not — Beads' stated reason for `bd-a1b2`.
- Per-machine lookup caches (org-id-locations, org-roam.db) must be rebuildable from the files, and are the thing that goes stale when files move under git.

## A link vocabulary for Relay

**What converged.** Across every tracker read, the typed vocabulary that users actually fill is the same four, plus one that agents need:

| relation | who has it | why it survives |
|---|---|---|
| `blocks` / blocked-by | GitHub dependencies (2025), Linear, Jira default, Beads (the *only* class that changes `bd ready`) | it changes scheduling; it is the one type a reader acts on |
| `parent` (sub-issue) | GitHub sub-issues, Linear parent/sub-issue, Jira epic/subtask, Beads `parent-child`, hierarchical ids `bd-a3f8.1` | containment; auto-close and roll-up depend on it; every system keeps it structural, not as a generic link |
| `duplicate` | GitHub close reason, Linear reserved status, Jira `duplicates`/`is duplicated by`, Beads `duplicates` | it closes the source; Linear and GitHub make it a *state* with a pointer |
| `related` | Linear (auto from mentions), Jira `relates to`, Beads `related`, Obsidian/org backlinks in general | the untyped default; a mention in prose is already this |
| `discovered-from` | Beads only, but it names what `cases.jsonl` and threads already record | provenance from an agent turn: "filed while working on #X" |

Everything beyond that is drift: Jira admins add `causes`, `reviews`, `implements`; Beads grew to ten types and had to document which six are "graph annotations only". Relay's `links` front matter already encodes the other useful edges as **fields whose name is the type**: `plans`, `commits`, `evidence`, `related`, `github`, plus `blocked_by` and `parent` — that is the Obsidian-properties / Tana-field model, and it should stay a small fixed set of keys rather than a free relation vocabulary. Recommendation: keep `blocked_by`, `parent`, `related` as is; add `duplicate_of` (single-valued, and setting it closes the card, as Linear and GitHub do); add `discovered_from` (single card id, written by the deliver skill when it files a card mid-turn); add `supersedes` on work cards the way memory cards already have it. Do not add `caused_by`, `validates`, `tracks`: no system shows users filling them.

**Address forms for non-card targets.** Every system that scales past one object kind uses a *sigil or prefix on the same token shape*, not a different syntax: GitHub `#26` vs `owner/repo#26` vs `owner/repo@sha`; org `id:` vs `file:` vs `doi:`; Anytype/Tana typed fields. So:

| target | address | stability |
|---|---|---|
| card | `#K7Q2` | content-stable 4-char id; alias cards for renames |
| skill | `skill:deliver` (id, and `skill:deliver@sha256:…` when a case pins a version, as `cases.jsonl` already does with `server_version`) | id + optional digest |
| memory | `#K7Q2` — memory cards share the card id space; `supersedes` chains replacements, `paths` scopes them | card id |
| run / case | `case:c-47b86eb0` (the `cases.jsonl` `id`) | ledger id, append-only |
| artifact | `artifact:<path>@<commit>` for files in git; `artifact:<run-id>/<name>` for run outputs | GitHub permalink rule: path alone is not stable |
| commit | bare 40-hex sha, or `@sha` after a repo name for another repo (`links.commits` already does this) | immutable |
| pane / session | `pane:<session-id>` — live, so *never a stored link target*; store the case or turn id it produced instead | ephemeral |
| line of code | `path:line@sha` (org's `::` search as fallback when only path is known) | pinned to commit |

All of them should be plain tokens that `rg` finds: `rg '#K7Q2' .board/` must return every reference, which rules out link forms that encode the id (URL-escaping, wrapping in `[[ ]]` with a title first).

**Stored vs computed backlinks.** The evidence is one-sided. Every file-based system stores forward links only and computes the reverse (Obsidian, org-roam, Logseq, Dendron, Foam, Anytype); the systems that store both ends do so inside one server transaction (Notion two-way, Linear, Jira) or as an append-only *event* rather than a field (GitHub cross-reference timeline); and the stored reciprocal that crosses a system boundary is the one Atlassian documents as drifting with "root cause unknown". Beads shows the git-side version of the problem: an exported edge row merges, but its absence cannot mean deletion. So for Relay: **forward links live in the source card's front matter or prose; the reverse is an index rebuilt from the files** (like org-roam's db: per-machine, incremental, never committed, and rebuilt from scratch when a file is reloaded from disk — the exact case Logseq #7362 got wrong). The one stored reverse worth having is the GitHub shape: an append-only line in the *thread file* of the target ("mentioned in #X, 2026-09-25, by codex"), which merges as a text append and doubles as the `rg`-readable backlink when Relay is not running. If a thread line and the index disagree, the index wins, because it was computed from the forward links.

## Traps

- **Stale two-way links.** Jira/Confluence "Mentioned in" missing with "root cause is unknown at this time"; workaround is to clone the page ([Atlassian KB](https://support.atlassian.com/jira/kb/mentioned-in-confluence-page-is-not-displaying-on-individual-jira-issues/)). Notion avoids it only by having one writer for both ends ([Relations](https://www.notion.com/help/relations-and-rollups)). Two files in git each holding one end of a link will drift the first time two agents edit them in the same window.
- **Index treats a reload as a delete.** Logseq dropped every block reference to a file when Dropbox rewrote it ([#7362](https://github.com/logseq/logseq/issues/7362)). A Board index must be a function of the files, recomputed, not an event log patched on each change.
- **Deletion by absence.** Beads: "JSONL import is upsert-only; it cannot infer that records absent from an export were deleted" ([Sync concepts](https://raw.githubusercontent.com/gastownhall/beads/main/docs/core-concepts/sync-concepts.md)). If links are ever exported as rows, removing a link needs a tombstone or the source file's forward list is the only truth.
- **Title-based links break on rename outside the app.** Obsidian, Dendron and Foam all rely on the *editor* rewriting `[[name]]` links when a file is renamed ([Obsidian](https://obsidian.md/help/links), [Dendron](https://wiki.dendron.so/notes/g0iqmyiyxje6ndjmecshb8b/), [Foam](http://docs.foam.md/features/wikilinks)); a `git mv` by an agent or a merge that renames a file leaves dangling links that look identical to intentional links to not-yet-existing notes. The Zettelkasten rule stands: "you cannot change the title unless you change any reference to it" ([zettelkasten.de](https://zettelkasten.de/introduction/)). Relay's `#K7Q2` ids plus alias cards are the fix; never let a card be addressed by its file name.
- **Ambiguous name resolution.** Foam resolves duplicate file names "alphabetically (deterministic), and shows a warning" ([Wikilinks](http://docs.foam.md/features/wikilinks)); ids must be unique per project, and an id collision on merge must be an error, not a silent pick.
- **Graph-view noise.** "The full graph has become completely useless as the number of notes has grown" ([Obsidian forum](https://forum.obsidian.md/t/how-do-you-use-the-graph-view/2785)); Obsidian ships an "Existing files only" filter because dangling links clutter it ([Graph view](https://obsidian.md/help/plugins/graph)). Ship a local, depth-1 neighbourhood of one card (its `links`, its backlinks, its parent and children). Nothing vault-wide.
- **Over-typed relations nobody fills.** Beads reached ten dependency types and had to document that six are "graph annotations only" ([Dependencies](https://github.com/gastownhall/beads/blob/main/docs/core-concepts/dependencies.md)); Jira admins can define arbitrary named types and the KB shows nine defaults ([Link work items](https://support.atlassian.com/jira-software-cloud/docs/link-issues/)); Linear stayed at four for years and auto-derives `related` from mentions ([Issue relations](https://linear.app/docs/issue-relations)). The types that get filled are the ones that *do* something: block scheduling, close on duplicate, roll up to a parent, close on merge.
- **Two shapes for one edge.** Beads' `bd show --json` and `bd export` disagree on the dependency record and tooling got "silent nulls" ([#5592](https://github.com/gastownhall/beads/issues/5592)). One edge shape, in the front matter and in the index output.
- **Materialised resolved links in the file.** Foam's link reference definitions footer is off by default "to reduce clutter" ([Link reference definitions](http://docs.foam.md/features/link-reference-definitions)); a generated section in a card that several agents edit is a merge conflict factory. Generated reverse data belongs in the thread file (append-only) or the index (uncommitted), not in the card.
- **Long ids in prose.** Logseq users asked to "drop UUID for blocks in favor of short codes" ([discuss.logseq.com](https://discuss.logseq.com/t/drop-uuid-for-blocks-in-favor-of-short-codes/21219)); org only assigns a UUID on first link so most headings never carry one ([Handling links](https://orgmode.org/manual/Handling-Links.html)). Four characters is right for cards; for cases and runs keep the ledger id but let the UI show the card it belongs to.
- **Live things as link targets.** GitHub permalinks exist because "the version of a file at the head of branch can change" ([Permanent links](https://docs.github.com/en/repositories/working-with-files/using-files/getting-permanent-links-to-files)); a pane or session is the same kind of moving target. Link to what it produced (a case, a commit, an artifact at a sha), never to the pane.
